# BGE 系列 RAG 向量检索：索引、召回、重排与耗时配置建议

## 摘要：覆盖 1 万–3000 万条，768 维与 1024 维分别成表

对当前 3 万条、500 字符、768 维或 1024 维的中文 RAG 语料，若向量能够常驻内存且查询延迟预算在 50 ms 量级，**首选不是 HNSW 或 IVF，而是 Flat（精确）检索**。本机实测显示，N=3 万、d=768 时暴力内积仅需 2.48 ms；即使线性外推至 N=100 万，也仅约 82 ms。在实际的查询批处理、top-k 选择和系统抖动下，Flat 在约 10 万以内通常仍具竞争力；若要求 P95 低于 20 ms，建议以 **N≈30 万、单查询约 25 ms** 作为 Flat 的工程失效预警线，而不是机械套用固定行数阈值。[1]

从容量边界看，本报告覆盖 **1 万至 3000 万条共 11 个档位**，并对 768 维与 1024 维分别独立成表（见 1.1 与 1.2 节）。1000 万条 1024 维 fp32 向量仅原始数据就达 41 GB，叠加 HNSW 图边后 43.5 GB；3000 万条则达 123 GB / 130.6 GB（均为公式理论下限，工程预留需再计 20–30%），单机不再可行，须分片或磁盘原生方案（见 D 档）。因此，**30 万以内以 Flat 起步，100 万以内采用 HNSW M=32，300 万–1000 万转向 IVF+PQ+Refine，3000 万以上必须分布式**，是更符合内存约束的迁移路径。这里的核心分界不是单纯的数据行数，而是“原始向量及索引结构能否稳定留在 RAM 中”。

**两个维度的临界点不同步：1024 维的 Flat→HNSW、HNSW→PQ 切换点都比 768 维提前约一档。** 因为距离计算、原生内存、PQ 码本三者都是 1.33 倍关系，唯独 HNSW 图边与维度无关（M=32 时均为 256 B/向量）。1.3 节给出完整横向对照。

召回链路建议采用 **BM25 + BGE 稠密向量双路召回**。两路各召回 50 条，经 RRF（k=60）融合后保留 50–100 条，再由 BGE reranker 精排至最终 5–10 条。若团队希望减少一套 BM25 索引及词法特征维护成本，可采用 BGE-M3 的稠密与稀疏双输出；但查询文本短、术语约束强时，BM25 仍具有独立价值。

Cross-encoder reranker 的成本来源是 `候选数 × 一次完整 query–document 前向计算`，而且无法离线预计算。无 GPU 时，bge-reranker-large 处理 top-50 通常进入数百毫秒至秒级，不适合严格在线链路；base 或 v2-m3 短上下文场景相对可行，但仍需实测。一旦缺乏 GPU，应优先缩减候选数，再考虑“M3 多向量或延迟重排 + LLM 判断”等降级方案。[2]

最终建议是采用可灰度切换的四档架构：

- **A 档：1 万–30 万条，CPU 或少量 GPU**——Flat 为主，必要时 HNSW 兜底；
- **B 档：30 万–300 万条，单机多核或 GPU**——HNSW 为主；
- **C 档：300 万–1000 万条，内存受限**——IVF+PQ + 原向量 refine；
- **D 档：3000 万条以上**——分片 IVF+PQ、DiskANN 或托管向量库。

768 维与 1024 维在各档的具体索引、参数、耗时与内存，分别在 1.1 和 1.2 节独立成表，1.3 节给出横向对照。

硬件、更新频率、召回率 SLO、单节点内存和延迟预算尚未明确，因此本报告不固化单一配置，而是通过选型矩阵、参数边界和端到端预算提供可直接压测的起点。

## 1. 数据规模尚小，架构重点应从“选 ANN”转向“保证召回质量”

**当前 3 万条语料的主要问题不是近似索引失效，而是候选覆盖不足和重排质量不稳定。** ANN 是在内存、延迟和召回之间交换取舍的工具；当全量内积只需数毫秒时，提前引入训练、分桶和图索引，反而可能增加工程复杂度，却无法等比例换来质量收益。

本项目为 **3 万条中文 chunk**，每条约 500 字符、50 字符 overlap，约 350–500 token。BGE 候选模型包括：

- `bge-small-zh-v1.5`：512 维；
- `bge-base-zh-v1.5`：768 维；
- `bge-large-zh-v1.5`：1024 维；
- `bge-m3`：1024 维，同时支持稠密、稀疏和多向量输出。

reranker 候选包括 `bge-reranker-base`、`bge-reranker-large` 和 `bge-reranker-v2-m3`。当前模型选择已经限定了三个后续约束：

1. **必须保留完整 512 维、768 维或 1024 维向量**，不能直接截断维度；
2. **模型一经选定，索引必须与对应模型空间绑定**；
3. **检索阶段是召回质量与算力的第一道关口，reranker 无法弥补严重遗漏。**

**Flat 在约 10 万条以内通常仍是简洁且可靠的选择，但其有效边界取决于服务目标，而不是严格的时间常数。** 本机在 AMD EPYC Zen5、AVX-512、3 核容器、fp32、预归一化、单线程 BLAS 下测得：

|---|---:|---:|
| 1 万 | 768 | 0.68 ms |

| 10 万 | 768 | 8.16 ms |
| 30 万 | 768 | 24.8 ms |

结果严格接近 O(N·d)，即约 0.083 μs/条。在此基础上，top-k 的 `argpartition` 还需 0.1–0.5 ms。[1] 因此，对单查询 P95 50 ms 的服务，N=30 万已经接近应认真评估 ANN 的区间；但对离线批处理、后台检索或并发极低的内部系统，即使超过 30 万条，也不能仅凭这一数字判定 Flat 失效。

本报告将“暴力检索失效”定义为：**在满足目标召回率和 P95 延迟的前提下，Flat 持续劣于已调优的 HNSW/IVF。** 它不是“超过某个 N 就必须换索引”的硬阈值。由于目前缺少索引 SLO、并发数、CPU 核数和内存容量，下表以“值得上 ANN 吗”表达为条件性建议，而非绝对值。

| HNSW 图边（M=32） | 256 B/向量 | 256 B/向量 | 1.0x（与维度无关）[3] |
| PQ 码本（nbits=8） | 96 B/向量（m=96） | 128 B/向量（m=128） | **1.33x** [3] |
| Flat→HNSW 切换点 | 约 30–50 万 | 约 10–30 万 | **提前约一档** |
| HNSW→PQ 切换点 | 约 300–500 万 | 约 100–300 万 | **提前约一档** |
| 1000 万条 HNSW 内存（理论下限） | 33.3 GB | 43.5 GB | 1.31x |

*图 2：Faiss 官方 Flat 存储公式 `4d` 字节/向量，以及 HNSW 近似公式 `4d + 2·M·4` 字节/向量（M=32）得到的容量估算。数据来源：Faiss 官方索引文档 [3]；未计入库实现、对象头和碎片开销。*

**数据量本身不足以决定索引类型，全量数据能否驻留 RAM 才是更硬的分界。** Faiss 官方说明指出，IVF 将空间划分为 nlist 个 Voronoi 单元，查询只访问 nprobe 个最近单元，搜索时间大致随 nprobe 线性增长；Flat 则逐条计算距离，主要代价是 `N·d`。因此：

- 数据全量驻留内存，且 N 低于数十万时，Flat 的简单性和精确性具有明显优势；
- N 达到百万级，但单机内存仍充足时，HNSW 通常能以更高召回率和更低延迟服务；
- N 达到千万级，向量及索引无法稳定留在 RAM 时，才真正进入 IVF+PQ、IVF+PQ+Refine 或磁盘 ANN 的主场。[3][4]

**若必须预先在 3 万条环境部署 ANN，HNSW 优先于 IVF。** HNSW 无需训练，支持增量添加；IVF 则需要代表性样本训练聚类中心。对于会持续写入、修改和淘汰的 RAG 知识库，HNSW 的运维负担通常更低。IVF 更适合一次构建、批量导入、写多读多，或需要显式压缩码本的场景。

`IVF+HNSW` 可以结合粗量化与图搜索，但会同时引入训练过程和更长的调优链路，不建议作为 3 万条规模的首个实验对象。SCANN、DiskANN 则应在内存无法容纳图索引、或数据达到数千万至亿级时，再按实际部署环境单独评估。[4]

## 2. Flat 可用不代表任意存储格式都等效，fp16/int8 路径须先本地验证

**Flat 的配置重点不是“如何压缩”，而是保证度量正确、连续内存和高效 GEMM。** 预归一化使余弦相似度等价于内积，但错误的数据布局或算子选择，可能抵消甚至逆转“低精度更省、更快”的预期。

**Flat 必须采用 fp32 连续数组，并通过内积直接实现余弦。** 对 BGE 句向量先按行 L2 归一化，再执行 `IndexFlatIP` 或 `Q @ X.T`。在 batch 较小时，可手工控制 BLAS 线程；batch 较大时，应优先调用 `gemm`。

本机实测表明，使用 fp16 矩阵乘法并非默认更快：d=768 时，fp16 耗时 91 ms，反而比 fp32 的 2.5 ms 慢约 36 倍；int8 同样出现退化。因此，**“省内存就要改 fp16/fp32 混合存储”不能成立**。若目标是减少内存，应转向 Faiss SQ（Scalar Quantization）、PQ，或将主键与原文移出热索引。[1]

| 存储或执行项 | 推荐配置 | 依据及调优方向 |
|---|---|---|
| 向量 dtype | **fp32**；仅在高吞吐 GPU gemm 流水线成熟后，对副本评估 fp16 | 本机实测显示，CPU fp16 matmul 是慢路径；不要为了节省 CPU 检索内存而直接改算 fp16 [1] |
| 归一化 | 写入时一次完成，查询向量在线归一化 | 余弦因此退化为内积，可直接使用 `IndexFlatIP` |
| 数据布局 | (N, d) 行主序、对齐、连续 fp32 | 有利于 BLAS 顺序访问和批处理；top-k 通过 `argpartition` 完成 |
| 距离计算 | 单条内积；批量时使用 `matmul` | 本机实测 batch=8 的 gemm 比单发快约 2 倍 [1] |
| 内存 | N×d×4 字节 | 3 万×768≈92 MB；3 万×1024≈123 MB [1] |
| top-k | `np.argpartition(-sim, k)` | 额外约 0.1–0.5 ms；最终输出仍需对 k 个结果排序 |

**IVF 的调优核心是训练充分、分桶均衡，并以 nprobe 在线交换召回和延迟。** Faiss 的搜索过程先通过粗量化器找到查询所在单元及邻近单元，再扫描被选中的倒排链。nlist 决定空间划分粒度，nprobe 决定实际访问的单元数；后者是可在线调整的召回—延迟旋钮。[3]

以下取值是**初始实验网格**，不是跨数据集不变的最优解：

| 参数 | 初始取值 | 含义及调优方向 |
|---|---:|---|
| nlist | `4√N` 为起点（向上取到 2 的幂次便于对齐）；可比较 `√N`、`2√N`、`4√N` | nlist 过小，倒排链过长；过大，则单元过空或 nprobe 必须增加。N=100 万时 `4√N`=4000，实际取 **4096**（2¹²）；N=1000 万时取 16384 |
| nprobe | 召回目标为 0.95 时，从 `0.05·nlist` 起 | 增大可提升召回率，但增加分桶扫描、距离计算和 top-k 维护成本 |
| 训练样本 | ≥ `39·nlist`；且尽量代表真实语料 | 样本不足会使聚类中心失真；Faiss Wiki 给出的是训练充分性经验要求，而非保证某个召回率的充分条件 [5] |
| 粗量化器 | `IndexFlatIP` 或 `IndexFlatL2`，取决于度量方式 | 余弦路径下需预归一化，并与数据库度量保持一致 |
| 度量 | 与索引及归一化策略完全一致 | 同一 collection 内不得混用 L2 与 IP |

以 N=100 万、nlist=4096（`4√N`=4000 向上取 2¹²）为例，建议先测试 nprobe ∈ {32, 64, 128}，并固定 Recall@50 和 P95 延迟。若 nprobe=128 仍无法达到目标，应先增加 nlist 并重新训练，而不是无限提高 nprobe：后者最终会退化成扫描大部分倒排链，失去 IVF 的剪枝意义。

> **nlist 取值口径**：本报告统一以 `4√N` 为起点并向上取到 2 的幂次，故 N=100 万时全文一律取 **4096**（配套训练样本 ≥39×4096≈**16.0 万**），不再混用 4000 或 2048。若实测发现分桶过空、nprobe 需开得很大才能达标，可改试 `2√N`≈2048 并重新对比召回曲线。

**HNSW 在百万级 RAG 中最实用，但 M、efConstruction 和 efSearch 承担不同代价。** M 决定每个节点保持的连接数；efConstruction 控制建图时的搜索宽度；efSearch 控制查询时的候选搜索范围。前两项在索引构建后难以低成本修改，efSearch 则可在线上按请求调整。[3][6]

| 参数 | 推荐起点 | 影响及调优方向 |
|---|---:|---|
| M | 768 维：**16–32**；1024 维：**32**；内存充足且追求高召回时 **64** | 增大可改善连通性和召回，但增加图边内存及构建成本 |
| efConstruction | 100（平衡）；160–200（高质量）；最大不超过 400 | 主要增加构建时间和 add 时间；同时影响后续搜索质量 |
| efSearch | 召回约 0.90：32–64；约 0.95：100–160；约 0.99：200–320 | 每次查询的可调旋钮；增大提升召回，也会增加图遍历和距离计算 |
| 构建线程 | 与导入并行度匹配 | 高频增量写入时，提高 efConstruction 的成本会被多次构建放大 |

Faiss 官方索引文档给出 HNSW 的近似每向量额外内存公式：`2·M·4` 字节，再加上原始向量存储。[3] 因此，M=32、d=1024 时，图边额外占用约 256 B/向量；100 万条约为 256 MB，1000 万条约 2.56 GB。实际库实现、ID 映射和碎片还会带来额外开销，因此该公式只能用于容量下限判断，不能替代真实 RSS 测量。

公开 HNSW 基准进一步说明，efSearch 与延迟之间并非线性关系：efSearch 从 64 提高到 100，再从 100 提高到 150 时，召回率可由 0.925、0.95 升至 0.975，但平均延迟由约 42.5 ms 升至 55 ms 和 80 ms。[7] 这组数字来自特定数据集、库版本和硬件，不能直接套用到 BGE 向量，但它足以说明：**调整 efSearch 时，必须同时观察召回曲线和 P95，而不是只测平均值。**

**IVF+PQ 只有在千万级 RAM 受限，或需要在单机容纳多索引时，才有充分理由引入。** PQ 将 d 维向量拆分为 m 个子空间，每个子空间用 nbits 编码。Faiss 要求 d 能被 m 整除，因此：

- d=768 时，可采用 m=96、nbits=8，得到 96 B/向量的 PQ 码；
- d=1024 时，可采用 m=128、nbits=8，得到 128 B/向量的 PQ 码。

此时，倒排列表可只保存压缩码，显著降低存储，但距离比较也在压缩域近似完成，会引入不可忽略的召回损失。[3]

| 参数 | 推荐起点 | 含义及调优方向 |
|---|---:|---|
| m | 768 维：96；1024 维：128 | d/m 为子空间维度；应尽量保持各子空间足够表达 |
| nbits | 8 | 每个子空间有 256 个码字；4、8、12、16 的选择受 Faiss 实现及质量约束 |
| nlist | 与 IVF 规则相同；千万级可从 8192 或 16384 起 | 需结合真实分布扫描并重建 |
| nprobe | 从 8–32 起，再扫描至 64–128 | 同时增加压缩距离计算和倒排链访问 |
| 训练集 | 至少覆盖所有子空间分布，通常数十万至数百万条代表性样本 | 分布漂移会直接破坏 PQ 码表 |

**PQ 召回损失没有脱离语料和参数后的“固定百分比”，工程上必须主动补偿。** 常见模式是：

1. 使用 IVF+PQ 快速召回一个较宽的候选池；
2. 从原始 fp32 向量或 SQ 副本恢复候选；
3. 用真实距离重排；
4. 再进入 BGE reranker。

Faiss 提供 `IndexIVFPQR`，也可通过 `IndexRefineFlat` 组合“压缩码检索 + 原始向量校验”。若只使用 `IndexIVFPQ`，在高精度 RAG 中建议将候选池放宽为最终需求的 2–5 倍，再通过原始向量精排，而不能直接把 ANN 的 top-k 当作最终候选。[3]

## 3. 双路召回应扩大覆盖率，但融合后必须受控，避免把成本转移给 reranker

**双路召回的目标不是让两路都“猜中答案”，而是从不同证据机制覆盖术语、短语和语义。** 但融合池一旦失控，节省下来的毫秒级检索成本会被 reranker 的线性增长迅速吞噬。

下文将“双路召回”明确为两条独立候选来源。每一路先召回较宽候选，再通过 RRF 或去重合并，最后截断为一个受控池。对中文短查询、专业术语和 exact phrase 约束较强的场景，BM25 的互补价值较高；对概括性、同义转述类问题，稠密向量价值更高。因此，RRF 不应对两路结果预先赋予固定置信度，而应通过排序位置自然平衡。

### 稠密向量 + BM25 双路召回

该组合是默认方案。向量侧使用 bge-base/large/M3 的 768 或 1024 维稠密向量；文本侧使用 Elasticsearch、OpenSearch、Lucene 或 BM25Okapi 的稀疏倒排索引。两路均返回带分数的文档 ID 及来源标记。

RRF 使用 `score=Σ 1/(k+rank_i)`。建议 **k=60**，两路权重均为 1.0。该 k 值是公开 RRF 研究的常用起点，并非 BGE 专用魔法参数；若一路长期只贡献噪声，应通过离线 nDCG/Recall 分析降低其候选数或淘汰该路，而不是给 BM25 硬设 0.3、稠密向量硬设 0.7。[8]

| 环节 | 推荐数量或参数 | 设计理由 |
|---|---:|---|
| 稠密路候选数 | **50**（宽松质量时可 100） | 覆盖语义邻近，但避免后续重排爆炸 |
| BM25 候选数 | **50**（高术语约束时可 100） | 覆盖词面匹配及短查询，避免同义词遗漏 |
| 融合算法 | RRF，k=60，等权 | 对异构分数天然归一；若某一路系统偏置明显，再改 rank-aware ensemble |
| 融合后去重 | 按 chunk_id | 同一物理 chunk 的多个来源只保留最高 RRF 分 |
| 进入 reranker 的池大小 | 50–100；在线严格预算下 **20–50** | 保证召回，同时约束 cross-encoder 成本 |
| 最终 top-k | **5**（标准）；复杂 QA 可用 **10** | 与 BGE reranker max_length 及生成上下文窗口匹配 |

若稠密侧采用 HNSW，应设置 `efSearch` 以满足 Recall@100，而不是仅满足最终 top-5。ANN 的小 k 精确性并不代表大候选池覆盖率足够：前者只要求最靠前几项准确，后者还要求相关文档不遗漏。

### BGE-M3 稠密 + 稀疏双路

BGE-M3 可同时输出 1024 维稠密向量和 lexical weight 稀疏向量。稠密侧可进入 HNSW/IVF，稀疏侧可进入稀疏倒排索引，两者再进行 RRF 融合。其优势是只需维护一套 embedding 服务和模型版本，不需要单独维护 Elasticsearch 词法索引。[9]

| 环节 | 推荐数量或参数 | 设计理由 |
|---|---:|---|
| M3 稠密候选 | **50** | 承接语义扩展和同义匹配 |
| M3 稀疏候选 | **50** | 承接显著词、专有名词和精确短语 |
| 融合 | RRF k=60，等权 | 与上一模式保持接口一致 |
| 融合池截断 | 50–100 | 后续成本与召回率的平衡区间 |
| 重排 | bge-reranker-v2-m3 或 base/large | v2-m3 可处理长候选，base/large 通常更适合 512 token 以内交互 |

**M3 双路降低运维复杂度，但不能因此取消传统 BM25。** M3 稀疏输出仍是模型学习得到的词权重，并非基于词项的传统 BM25 索引；它是否能够覆盖精确停用词、字段权重和自定义分词规则，必须在线下评估集上验证。

若现有系统已有成熟的 BM25 索引，且查询显著受术语约束，建议保留“稠密 + BM25”。若团队追求单一模型、单一部署和较低运维成本，可采用“M3 稠密 + M3 稀疏”，并通过 query 日志持续比较两者在召回率上的差异。

### 双粒度 chunk 两路召回

小 chunk 适合回答聚焦问题，大 chunk 能够提供上下文和跨句证据。建议固定物理存储为大 chunk，逻辑检索时由大 chunk 拆分为小 chunk；或同时保留两套 ID，使小 chunk 命中后能够映射回完整大 chunk，避免将上下文不完整的片段送入生成器。

| 环节 | 推荐配置 | 设计理由 |
|---|---|---|
| 小 chunk | 512 token，50 token overlap | 与 BGE 典型输入粒度及 base/large 512 上限兼容 |
| 大 chunk | 1024–2048 token | 提高跨句连贯性；若大于 2048，需截断或摘要 |
| 小 chunk 召回 | 向量 top-50 | 捕获局部匹配 |
| 大 chunk 召回 | 向量 top-20 | 保留完整上下文 |
| 映射规则 | 小 chunk → 父大 chunk；同大 chunk 去重后保留最高分 | 防止一个大 chunk 的多个子片段挤占最终列表 |
| RRF 池 | 50–100 | 先融合，再交给 reranker |
| reranker 输入 | 大 chunk 文本，必要时拼接命中小段 | 避免 cross-encoder 只见半截上下文 |

**rerank 必须在 chunk 边界对齐的前提下进行。** 若索引保存的是小 chunk 向量，而最终返回大 chunk，重排分数应绑定大 chunk ID，否则同一文档的不同子片段会在 top-k 中重复，并扭曲最终多样性。

若使用 bge-reranker-base/large，query 和 passage 拼接不得超过 512 token，必要时应按证据段截断；v2-m3 支持更长输入，适合长候选，但也会增加逐 pair 计算量。[2]

## 4. reranker 成本由候选数和长序列前向计算共同决定，CPU 不应成为默认在线方案

**reranker 的在线成本近似随候选数线性增长，GPU、短文本和批处理只能改善常数，不能消除 `top_k × forward` 的结构性代价。** 因此，池大小必须先受控，模型选择才谈得上边际收益。

cross-encoder 将 query 和每个候选 passage 拼接后进行完整 Transformer 前向计算。以 bge-large 类为例，hidden=1024、FFN=4096、24 层，本机按 GEMM FLOPs 估算，其每 token 计算量约为 base（h=768、FFN=3072、12 层）的 3.56 倍。[1] 由于 RAG 的 query 通常较短，序列长度主要由 passage 决定，因此 reranker 成本可近似写作：

`候选数 × pair_forward(L_q + L_passage)`

该成本无法离线预计算，因为 query 在请求时才出现。GPU 并行和批处理只能降低每个 pair 的固定开销；当候选数上升时，成本仍会线性放大。

### 进入 reranker 的池大小与最终 top-k

| 场景 | 融合后进 reranker 的候选数 | 最终 top-k | 说明 |
|---|---:|---:|---|
| 严格在线，CPU 或 T4 小卡 | **20** | 3–5 | 将重排开销置于可控范围 |
| 标准在线，A10/4090 或 GPU 批处理成熟 | **50** | 5 | 推荐默认档 |
| 高召回离线评估 | **100** | 5–10 | 测量召回增益，不建议作为常态在线值 |
| 极端质量探索 | 100–200 | 10 | 必须配合模型批处理、异步队列，或后置 LLM 过滤 |

**池大小应先满足 Recall@rerank，再考虑业务 top-k。** 建议离线构造 300–1000 条 query 及 qrels，检查：

- 正确答案是否位于稠密 top-100；
- 是否在 BM25 top-100；
- 是否在 RRF 后 top-50；
- 是否最终位于 rerank top-5。

若正确答案未进入候选池，调整 reranker 模型或交叉特征并无帮助，应先扩大双路召回数，并检查 query 改写、过滤器和 chunk 质量。

### BGE reranker 公开耗时：只能用于量级决策，不能替代同机基准

以下数据来自公开实测或第三方工程页面，软硬件、序列长度、批大小和 torch 版本均不一致。它们应被视为**量级锚点，而不是上线承诺**；本机实测中的 GEMM 成本及公开数据方向可用于解释趋势。[1][2][10]

| 模型 | 精度及批处理 | CPU 单次调用量级 | 入门/中端 GPU 量级 | 使用判断 |
|---|---|---:|---:|---|
| bge-reranker-base（278M，L≤512） | fp32；未特别说明时近似单条或约 10 级候选 | **约 120–250 ms/请求（候选约 10–50）**；多核不保证线性加速 | T4/A10/4090 短候选约 **20–50 ms**，批处理可进一步下降 | CPU 在线可行的前提是候选较少、并发较低；GPU 可稳定支撑 20–50 |
| bge-reranker-large（560M，L≤512） | fp32；单候选 | 第三方 100 文档报告约 **400 ms/请求量级**；本机高维 GFLOPs 与其量级方向一致 [1][10] | RTX 3080 类报告约 **50–150 ms/请求量级** [10] | top-50 不适合无 GPU 的严格在线链路；模型较大且固定开销明显 |
| bge-reranker-v2-m3（568M，L≤8192） | fp16；批量 | i7-11800H 类 CPU：20/30/53 候选约 **386/952/2215 ms** [2] | 同机 RTX 3060 Laptop：20/30/53 候选约 **124/317/786 ms** [2] | 长文档或高候选数 CPU 不可行；GPU fp16 + 批处理收益明显 |

第三方页面给出的另一组 v2-m3 数据为：RTX 4090 单条约 12.3 ms，批量 32 约 98 ms；Intel i9-13900K 单条约 125 ms。[13] 这组数字与前述移动端 RTX 3060 结果存在明显差异，进一步说明**模型、显存、批大小、序列长度和 torch 后端必须同时锁定**，单独比较“GPU 快几倍”没有生产意义。

上述数据的共同约束是：large 类模型参数更多，1024 维 embedding 的前向计算也更多；GPU fp16 及批处理能够改善吞吐，但无法把“候选数 × pair forward”变成常数时间。公开基准的一致方向是，GPU 通常比 CPU 快约一个数量级，但相对加速比会随候选数、序列长度和批大小变化。[2][13]

**CPU 上能否运行 BGE reranker，应按查询负载和模型大小分层判断。** 本机实测还表明，CPU 多线程及攒批对 encoder 有增益，但并非所有算子都能线性加速：d=1024 比 d=768 更偏向 memory-bound；768 维 L=32 时，3 线程约获 2.4 倍加速，1024 维时降至约 1.5 倍；攒批 batch 3–9 可额外获得 1.4–1.7 倍增益，且两者可以叠加。[1]

这意味着 CPU 上的“理论节省”未必能转化为在线服务收益。若系统被内存带宽或动态 Python 调度限制，增加核数可能不会等比例减少端到端 P95。

| 条件 | bge-reranker-base | bge-reranker-large | v2-m3 |
|---|---|---|---|
| CPU、top-20、低并发、交互可等约 1 秒 | 可评估 | 勉强，需实测 P95 | 不推荐 |
| CPU、top-50、交互要求 <500 ms | 通常勉强 | **不可行** | **不可行** |
| T4/A10 + fp16 + batch 20–50 | 可行 | 可行 | 可行，但长输入需压测 |
| 4090/A100 + 成熟批处理 | 高吞吐 | 高吞吐 | 高吞吐 |

**若无法使用 GPU，合理降级顺序不是直接删除 rerank，而是逐级降低候选与上下文成本。**

1. **首选：**保持双路召回，将融合池从 100 缩减至 20，并将 passage 截断至 256–384 token，仍使用 bge-reranker-base。
2. **次选：**采用“稠密 top-100 → 原向量精确重排 top-20 → LLM 只做最终相关性或冲突判断”，减少 cross-encoder 调用。
3. **若 M3 基础设施已经成熟：**使用 M3 的 ColBERT 多向量 late interaction 进行候选精排。它能够利用查询和 passage token 的多向量相似度，通常比单向量精细，但仍需额外的多向量索引和计算。应将其视为重新排序组件，而不是替代所有 rerank。
4. **只有在质量评估允许时：**取消 cross-encoder，采用 RRF 后 top-10，并将 LLM 作为最终过滤器。

任何降级都必须通过 Recall@5、MRR 和错误案例分析验证。减少 rerank 候选可能造成“回答更快，但召回更差”，因此不能只以延迟达标作为上线依据。

## 5. 端到端预算必须由真实 P95 驱动，离线基线只能用于结构拆分

**当前最可信的成本边界来自本机 Flat 实测，但单查询数字不能代表并发后的线上 P95。** 工程预算应把编码、检索、融合、重排和原文加载拆开，再按真实负载叠加。

### 单查询组件耗时模型

| 组件 | 计算内容 | CPU 估算 | GPU 估算 | 调优抓手 |
|---|---|---:|---:|---|
| Query embedding | BGE encoder 一次前向 | base L=32 约 37 ms；L=512 约 411 ms，参考本机 GEMM 锚点 [1] | 通常 5–20 ms，取决于模型、精度和 batch | 缓存常见 query；批处理；必要时裁剪 query |
| 粗检索 | 图遍历、分桶扫描、距离计算和 top-k | Flat：约 0.083 μs/条×N×d/768；HNSW：约 5–30 ms；IVF：约 3–20 ms | 通常低于 CPU，但需计入 PCIe/H2D | 选索引、调整 nprobe/efSearch、量化 |
| 融合及去重 | RRF、ID 映射、父 chunk 归并 | 通常 <2 ms | 同左 | 限制池大小，减少重复映射 |
| Rerank | `K × pair forward` | base 短候选约 100–250 ms；large 约 400 ms；v2-m3 长候选更慢 [2][10] | 20–150 ms，取决于候选、批处理和长度 | **先缩减 K，再选择模型和 GPU** |
| 取原文及组装 | KV、对象存储或数据库读取 | 通常 2–20 ms | 同左 | 预热、本地缓存、只取最终 top-k |

本机 anchor 的关键价值是确认：当前 **3 万 × 768 的 Flat 检索成本约 2.5 ms，远低于 CPU 上大型 reranker 的成本量级**。因此，在 3 万条规模过度优化 ANN，却不能同步优化 rerank，属于局部优化。

### 目标预算 A：交互式 RAG，端到端 P95 ≤ 500 ms

| 链路 | CPU 单路估计 | GPU 单路估计 | 占比判断 |
|---|---:|---:|---|
| Query embedding | 40–200 ms（base/large，未量化） | 5–20 ms | CPU 链路的主要成本之一 |
| 双路召回 | Flat 约 3–10 ms；HNSW 约 3–20 ms | <10 ms | 小头 |
| 融合及原文主键查询 | 1–10 ms | 1–10 ms | 小头 |
| Reranker top-20/50 | base 约 100–250 ms；large 约 300–800 ms | base/large 约 20–100 ms | **CPU 链路的绝对主导项** |
| 最终取原文及返回 | 2–20 ms | 2–20 ms | 小头 |
| **合计** | **约 150–500 ms，large 常超预算** | **约 30–150 ms** | GPU 显著改善尾部延迟 |

要达到 500 ms SLO，CPU 场景需要至少满足以下三项：

- 使用 base 而非 large；
- 将 rerank 候选控制在 20；
- query encoder 已量化或充分缓存。

若采用 bge-reranker-large 且候选为 50，CPU 几乎必然突破预算。GPU 场景则可使用 base/large，并将池大小保持在 50。[2][10]

### 目标预算 B：严格交互，端到端 P95 ≤ 150 ms

| 决策项 | CPU 可行性 | GPU 建议 |
|---|---|---|
| Query encoder | 需 ONNX/TorchScript、int8 或短 query，且不能频繁冷启动 | fp16，必要时批处理 |
| 稠密检索 | Flat/HNSW，要求 <10 ms | <5 ms |
| 融合池 | **20**，最多 50 | 20–50 |
| Reranker | 不建议 large；base 短候选仍需实测 | base/large，批处理 20–50 |
| 原文加载 | 必须预热或缓存 | 必须预热或缓存 |
| **总体判断** | 仅在候选较少、模型量化成熟且并发较低时可行 | 推荐方案 |

本机实测显示，BERT 类 encoder 的 L=512 纯 GEMM 累加约为 L=32 的 11 倍，这说明**查询长度和序列裁剪会同时影响 encoder 与 reranker**。在保证语义完整的前提下统一裁剪 query、title 和 passage，通常比只在 embedding 侧截断更有效。[1]

## 6. 落地配置应四档可切换，上线前必须补齐实测基线

**当前 3 万条语料的正确策略不是立即上 HNSW，而是先建立“Flat 真值 + 未来 ANN 切换点”。** 随着数据增长，再依次迁移至 HNSW 和 IVF+PQ，避免在小规模阶段提前承担训练、压缩和图维护成本。

### A 档：1 万–30 万条，CPU 或少量 GPU

该档适用于当前状态及未来中短期增长。

```python
# Faiss 伪代码：A 档 Flat 精确基线
faiss.normalize_L2(xb)
index = faiss.IndexFlatIP(d)  # d=768 或 1024
index.add(xb)

# 在线
faiss.normalize_L2(xq)
D, I = index.search(xq, k=100)  # 先召回足够候选，再做 RRF/rerank
```

对应配置如下：

| 模块 | 推荐配置 |
|---|---|
| Embedding | bge-base-zh-v1.5（质量、速度、内存平衡）；确有高难语义需求再评估 large/M3 |
| 向量索引 | **FlatIP**；为未来兼容预留 HNSW |
| HNSW 备选参数 | M=32，efConstruction=160，efSearch=128 |
| 稀疏路 | BM25（推荐）或 M3 稀疏 |
| 召回 | 稠密 50 + BM25 50，RRF k=60，池 50–100 |
| Reranker | GPU：base/large；CPU：base + top-20 |
| 最终 top-k | 5 |

若后续发现单查询 P95 稳定超过预算，或并发上升后 CPU 无法承受全量扫描，应切换至 HNSW，而不是直接压缩向量。压缩会引入近似损失，而当前规模下 HNSW 通常足以覆盖查询负载。

### B 档：30 万–300 万条，单机多核或 GPU

| 模块 | 推荐配置 |
|---|---|
| 默认索引 | **HNSW32**：`IndexHNSWFlat(d, 32)`；efConstruction=160 |
| 高召回场景 | efSearch=160–256 |
| 低延迟场景 | efSearch=64–100 |
| 高更新量场景 | 评估 `IVF-Flat`；nlist=4096（100 万，与 1.1/1.2 节口径一致），nprobe 从 64 起 |
| 内存紧张时 | SQ8 原始向量，或转向 IVF+PQ |
| Reranker | GPU 的 base/large，池 50；CPU 仅考虑 base 及池 20 |

**从 Flat 迁移至 HNSW 前，必须保留 Faiss 真值索引。** 应使用固定 query set 验证 Recall@100 和召回覆盖率，再比较 P95。否则，HNSW 即使更快，也可能因图参数不当造成系统性遗漏，而这种遗漏不会体现在平均延迟中。

### C 档：300 万–1000 万条，单机内存受限

**进入 C 档后，主约束从"延迟"变成"内存"，因此 PQ 压缩成为必选项而非可选项。** 768 维与 1024 维的 PQ 参数不同（m=96 vs m=128），前者压缩到 96 B/向量，后者 128 B/向量 [3]。

```python
# Faiss 伪代码：C 档 IVF+PQ + Refine（以 d=1024、N=500 万为例）
quantizer = faiss.IndexFlatIP(d)
index = faiss.IndexIVFPQ(quantizer, d, nlist=8944, m=d//8, nbits=8, metric=faiss.METRIC_INNER_PRODUCT)
index.train(train_vectors)   # >= 39 * nlist = 34.9 万，且分布具有代表性 [5]
index.add(xb)
index.nprobe = 64            # 扫描至 128

# 用原始 fp32 向量精排：IndexRefineFlat 或手工两阶段
coarse_D, coarse_I = index.search(xq, k=200)
```

| 模块 | 768 维（m=96，PQ 码 96 B/向量） | 1024 维（m=128，PQ 码 128 B/向量） |
|---|---|---|
| 500 万条 PQ 码本 | 480 MB | 640 MB |
| 1000 万条 PQ 码本 | 960 MB | 1.28 GB |
| nlist | 8944（500万）／12649（1000万） | 同左（nlist 只与 N 有关） |
| nprobe | 64 起，扫描至 128 | 64 起，扫描至 128 |
| 训练样本 | ≥ 34.9 万（500万）／≥ 49.3 万（1000万） | 同左 [5] |
| PQ 粗召池 | 200–400 | 200–400 |
| 原向量精排 | top 50–100（需从冷存储取回 fp32） | top 50–100 |
| Reranker | GPU base/large，最终池 50 | GPU base/large 或 v2-m3，池 50 |
| 最终 top-k | 5–10 | 5–10 |

**C 档不能跳过原始向量 refine，直接将 PQ 距离送入 cross-encoder。** 对高精度 RAG 而言，应先恢复候选精度，再让 reranker 判断语义相关性；否则压缩误差会污染后续所有阶段。

**fp32 原始向量在 C 档应视为冷数据。** 1000 万条 1024 维的原始向量是 41 GB，只需在 refine 阶段按 ID 取回 50–100 条，可存放于对象存储或列式库，通过 ID 点查获取 [3]。

### D 档：3000 万条以上，必须分布式或磁盘原生

**3000 万条时，768 维需要 92 GB、1024 维需要 123 GB 仅存原生 fp32 向量，任何单机方案都不成立。** 此时索引选型已不是单机库的参数问题，而是架构分层问题 [3][4]。

| 方案 | 768 维 | 1024 维 | 适用条件 |
|---|---|---|---|
| **分片 IVF+PQ**（按业务/时间分片，查询扇出后归并） | 92 GB → 8 分片 × 11.5 GB | 123 GB → 8 分片 × 15.4 GB | 有天然分片键（租户、业务线、时间）时首选 |
| **DiskANN / Vamana**（图索引驻留 SSD） | 单机可承载，延迟 10–50 ms 量级 | 同左，延迟略高 | 无分片键、但可以接受 SSD 随机读延迟 |
| **SCANN**（各向异性量化） | 适合高 QPS 批量检索 | 同左 | 吞吐优先、对召回率要求可放宽到 0.90 |
| **托管向量库**（Milvus/Pinecone/腾讯云等） | 运维外包 | 同左 | 团队无专职 infra 时的务实选择 |

**D 档的选型依据从"哪个索引更快"变成"数据能否按查询模式切分"。** 若 90% 的查询都能路由到单个分片（如按租户隔离），分片 IVF+PQ 的性价比远高于任何单机图索引；若查询必须全库扫描，才需要考虑 DiskANN 或托管方案。

这一档已远超当前 3 万条规模的规划范围，仅列出以避免"索引选型看起来只到千万级"的误解。**实际工程中，从 A 档迁移到 D 档通常伴随架构重写，而非单纯换索引参数** [4]。

### 上线前必须完成的压测基线

1. **建立精确基线。** 使用代表性中文 query 集合，测量 Flat 的 Recall@20/50/100，并保存为 ANN 调参真值。
2. **确定查询长度分布。** 真实测量 P50/P95/P99 的 query、chunk 和拼接后序列长度；不得只测 `L=32` 或 `L=10`。
3. **锁定 reranker 负载。** 在目标候选数 20/50/100、batch 1/8/32 下，分别测量 base、large 和 v2-m3。每个配置至少记录模型加载、首请求、P95、显存和 RSS。
4. **使用全链路并发压测。** 将 query encode、索引、融合、rerank 和原文读取置于同一服务链路，记录 P95，而不是将各阶段最小值相加。
5. **评估内存。** 分别测量原始向量、HNSW 图边、倒排列表、PQ 码和 ID 映射的真实 RSS，并与 Faiss 公式估算交叉校验。[3]
6. **建立回归集。** 为每个索引版本固化 qrels、query 改写、metadata filter、chunk 映射和 top-k 规则。模型或索引重建后，自动比较 Recall@5、MRR、P95 和内存。
7. **明确模型切换代价。** 更换 BGE 模型后必须全量重建索引；双路召回中的一路发生显著漂移时，也应重测融合权重。
8. **将 SLO 映射为可观测指标。** 对“<50 ms、<150 ms、<500 ms”分别定义并发、P95 样本窗口和失败阈值，避免以单查询均值判断上线资格。

**BGE base/large 向量不支持 Matryoshka 截断。** bge-base-zh-v1.5 和 bge-large-zh-v1.5 的训练语义绑定完整维度；直接截取前 256 或 512 维会得到损坏向量。任何“换 embedding 模型”或“改维度”的操作，都应触发全量重建、离线回放和召回回归。[9]

若团队确有降维需求，应重新训练具备 Matryoshka 特性的模型，或使用经真实数据验证的投影方案，而不能对生产向量直接切片。

## 结论：3 万条语料应先保证召回与可控延迟，再随规模逐步迁移索引

**当前最稳妥的架构是“Flat 精确召回 + BM25 双路 + GPU rerank”的可演进组合。** 在 3 万条数据下，暴力检索约 2.5 ms，不是系统的主要瓶颈；若仅为了减少数毫秒检索时间而引入 HNSW 或 IVF，反而可能增加训练、一致性和运维负担。[1]

随着数据增长，建议遵循以下迁移顺序：

1. **30 万条以内（768 维）／10–30 万条（1024 维）：**维持 Flat，通过并发、批处理和缓存判断真实 P95；
2. **超过切换点、延迟预算趋紧时：**切换到 HNSW（M=32），以 efSearch 在线平衡召回和延迟；
3. **300 万–1000 万条或受内存约束时：**转 IVF+PQ（768 维 m=96／1024 维 m=128）+ 原向量 refine；
4. **3000 万条以上：**按分片键切分后 IVF+PQ，或采用 DiskANN／托管向量库——此时通常伴随架构重写，而非单纯换索引参数。

千万级不能用“1024 维 HNSW 一定很快”的假设指导容量规划。1024 维 fp32 向量及 HNSW 图边可能超过单节点 RAM，迫使索引换页，进而使 ANN 退化为磁盘扫描。此时，容量约束的重要性高于图索引的低理论复杂度。[3]

rerank 方面，GPU 不是“更快一点”的优化项，而是 large 模型进入严格在线链路的准入条件。候选数、序列长度和 pair 前向成本共同决定 rerank 阶段，CPU 多线程无法消除其结构性线性增长。

因此，推荐上线组合为：

- **当前 3 万–30 万条：**FlatIP + BM25 双路 + RRF；
- **候选池：**50–100；
- **最终 top-k：**5；
- **CPU 场景：**bge-reranker-base + top-20；
- **GPU 场景：**base/large + top-50；
- **1000 万条或内存受限：**IVF+PQ + 原向量 refine，GPU rerank。

上述配置必须结合实际 query 日志、候选长度分布、GPU 型号、可用内存和 P95 SLO 回归后再固化。当前证据足以确定迁移顺序和成本结构，但不足以在不压测的情况下承诺单一参数的全局最优。
