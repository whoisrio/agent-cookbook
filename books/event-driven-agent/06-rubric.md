# Stage 6：rubric 和 eval

## 需求：评价 agent 能力，是个天然的要求

传统软件一次任务的成功与失败有明确判据——单测断言、返回码、输出比对。agent 不一样：
同样一张任务单，这次做对了，换个 prompt 就开始绕路、漏报备、自作主张。
"改了 prompt、换了模型、重构了 loop，行为有没有变坏"没有答案——靠手感回归就是靠运气。

前五章每章末尾的"验证"小节全是人肉跑的。06 就是要把这件事变成机器可重复的。

## 地基：eval 不需要造新东西

eval = 重放录制好的 session + 对结果打分。零件前面都造好了：

- 3b 的落盘与位点 → 录制、重放
- 4 的投影 `f(log, policy)` → 重建"模型当时看到什么"
- 5 的压缩不变式 → 给定 `(log, policy_version)` → 唯一 messages

没有 log 就没有可重复的 eval。append-only 从 Stage 1 贯穿到 Stage 6，在这里收口。

## rubric：评价标准分三层

**第一层：红线（一票否决，硬断言）**

红线不是扣分项，是布尔门控：出现一次即整体 fail，其余分数作废。

- 越权写操作：该触发审批没触发、该报备没报备（3b 审批机制、fail-closed 的评分化）
- 破坏事实层：伪造工具结果、编造状态跳过流程
- 泄漏与越界：敏感信息外漏、操作超出授权范围

全部走事实层，程序判定，不经过 judge。

**第二层：能力（正常打分）**

回答"好不好"，允许 trade-off，可加权：

- 目标达成：任务单做完了吗？七个条目四种结局对得上吗
- 过程正确：工具选择与参数、指令遵循（rules.txt 的线守没守住）、对用户纠偏的响应
- 效率：几步、几次工具调用、多少 token 到达结果；该问人时问了，还是死磕重试

**第三层：体验（低权重，只看趋势）**

语气、友好、表述质量。LLM-as-judge 的领地，不进聚合分数的硬性门槛。

一句话：目标达成决定 agent 好不好，红线决定 agent 还是不是你想部署的那个 agent。

## 硬断言与软评分的分工

- 硬断言走事实层：工具调用序列对不对、redirect 补出来的消息形状合不合法、
  中断后状态完不完整、审批触发没触发——全可程序判定。
- 软评分走视图层：judge 的输入是模型当时看到的（压缩后的）上下文，报告注明这一点。
- 换过压缩策略的两次评测不可直接比较，需标注。

Stage 2~3 的行为语义全部变成 eval 用例：steering 生效时机、redirect 竞态降级、
插队不丢事件——以前靠手点，现在进回归集。

## eval harness

golden trajectories（录制）→ 重放 → 红线门控 → 硬断言 + rubric 评分 → 聚合报告。

- golden trajectory 的粒度 = 一个 session：存事实层 + policy_version，不存压缩后的 messages。
- 聚合报告不能是单一总分：红线是布尔门控，过了门再谈加权平均——
  否则"一次越权 + 高任务分"会伪装成及格。

## 要过的坎：LLM-as-judge 不稳定

同一轨迹两次打分不一样。处理：

- 评分输出结构化：强制 JSON + 逐项理由
- rubric 逐条独立判，不问"总体怎么样"
- 软评分只看趋势，不当断言用

## 关键论点

- agent 的评价标准不是"对/错"二值，而是分层：红线（能不能用）→ 能力（好不好用）→ 体验（喜不喜欢用）。

## 结尾
