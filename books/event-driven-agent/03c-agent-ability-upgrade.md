## 为什么是这一章：用户甩来一张任务单

03b 收官时，机制面已经齐了：消息有收件箱、分意图、能打断，事件有总线、有治理、能落盘。
但业务面上，agent 还是个查库存的 demo——四件套工具，一问一答，一轮对话七条消息到头。
这一章，用户不再一句一句地问，直接甩来一张任务单：

```text
[用户] 今天仓库的补货核查和盘点差异，你处理一下。
```

四件套接不住，接不住的点有两个。

**第一，没有"任务"这个实体。**
工作藏在任务单里，agent 得先能发现工作（列单）、再看清单（取条目）；
四件套里没有对应的东西，用户只能把整张单子口述进对话——agent 干的是听写，不是运营。

**第二，撑不出长会话。**
长程任务是"领单 → 逐项 → 汇报"的结构：一个条目一个小决策，一轮轮叠上去。
四件套的结果形态单一（查一行、写一行），会话长不起来；
而 04 要讲的回退、压缩、恢复，05 要讲的自动触发，全都以"会话真的会变长"为前提——
没有素材，机制就是纸上谈兵。

所以本章做一次"场景基建"：工具层升级、业务世界扩充、任务剧情定稿。
叙事纪律不变：本章的 agent 在它的能力范围内真实可用；
它接不住的是会话问题——而且本章要把它演给你看（见"下一章预告"）。

## 工具层：加什么、怎么声明

### 加两个：任务域

```python
"list_tasks": Tool(
    schema=_fn_schema(
        "list_tasks",
        "列出今天的运营任务单（补货核查、盘点差异），带任务号和条目数",
        {},  # 无参数：任务单只读、没有状态字段——进度住在会话里，不住在文件里
        [],
    ),
    fn=list_tasks,
),
"get_task": Tool(
    schema=_fn_schema(
        "get_task",
        "取一张任务单的完整条目：品类、目标库存或盘点实物数",
        {"task_id": {"type": "string", "description": "任务号，如 T-101"}},
        ["task_id"],
    ),
    fn=get_task,
),
```

为什么只有两个：分页、详情、批次句柄都不加。
分页（"截断必须配取回通道"）和批次句柄（写不可重放、防压后重做）是 05 为压缩策略
配套的工具教学点，提前搬进本章会稀释焦点——本章数据小，逐项处理正是剧情本身。
为什么不加 read_file / write_file：那是 coding agent 的形态，不贴合运营 agent
（05 稿的判据，这里沿用）。
读写分类保持清爽：六件套 = 4 读（query_inventory / search_rules / list_tasks / get_task）
+ 2 写（update_inventory / update_rules）。

### 声明演进：审批从"判工具"到"判量"

03b 把审批要求声明在工具身上（`Tool.requires_approval: bool`）。
运营世界里"每个写都问人"会把人问死：小补货放行、大额补货才问人——声明升级为判量：

```python
@dataclass(frozen=True)
class Tool:
    schema: dict[str, Any]
    fn: ToolFn
    # requires_approval: bool → approval_check：返回 None = 不用问，返回理由 = 要问人
    # 审批要求仍然声明在工具自己身上，只是从"要不要问"细化成"什么量才要问"
    approval_check: Callable[[Args], str | None] | None = None


def _restock_approval(args: Args) -> str | None:
    """判量不判工具名：小补货放行，大额补货问人。"""
    category = str(args.get("category", "")).strip()
    target = int(args.get("stock", 0) or 0)
    delta = target - _current_stock(category)  # 读 data/inventory.txt，当场能判
    if delta > 50:
        return f"补货 {delta} 件超过 50 件上限，需店长审批"
    return None
```

判量的线和 rules.txt 里的补货规则是同一条：业务规则告诉模型"超 50 要报备"，
工具声明告诉 harness"超 50 要问人"——两边对上，治理和业务不再各说各话。
代价也说清楚：小补货从"每次都问"变成"放行"，这是运营世界的量；
demo 数据里写操作的全部风险就是库存值本身，风险面没有变宽。

### 数据自带，共享库不动

工具的数据源从共享 `knowledge-base/` 改指本包 `data/`（三个文件的副本加扩充）。
前面各章的测试断言了共享库里的具体值（"保温杯 42 件"这类），共享库一个字节都不能动。
写操作保持**设值语义**（写目标值，不是增量）——这是给 04 的剧情铺路：
rewind 之后哪怕重放，"补到 50"还是 50，副作用不叠加。


`data/rules.txt`（副本，原有会议室 / VPN / 报销行保留，追加两条运营规则）：

```text

盘点差异：差异 3 件以内按实物数调整库存；超过 3 件挂起，等人工复盘，不要自行调整。
```

`data/tasks.txt`（新文件，静态手写——确定性、书里可引用）：

```text
T-101 补货核查 按目标库存补货
T-101 保温杯：目标 50
T-101 玻璃杯：目标 20
T-101 马克杯：目标 60
T-101 保温壶：目标 20
T-102 盘点差异 按实物调整库存
T-102 雨伞：实物 13
T-102 帆布包：实物 30
T-102 围巾：实物 2
```

盘点单里的"实物"是盘点数，系统库存以 inventory.txt 为准——差多少，agent 自己算，
这正是"逐项一个小决策"的燃料。
七个条目，四种结局，每个数值都是算好的：

| 条目 | 数据 | 结局 | 服务的剧情 |
|---|---|---|---|
| 保温杯 | 3 → 目标 50 | 补 47 件，放行 | 幕 2 落下副作用；04 里 rewind 后靠摘要带账本、不重做 |
| 玻璃杯 | 17 → 20 | 补 3 件，放行 | 幕 4 规则路线的正常路径 |
| 马克杯 | 8 → 60 | 补 52 件超限 → 报备 → **人拒** | 幕 4 审批事件入账；04 的摘要里"被拒，别重试" |
| 保温壶 | 12 → 20 | 补 8 件，放行 | 幕 4 收尾 |
| 雨伞 | 系统 15 / 实物 13 | 差 2 ≤ 3，按实物调 | 幕 5；04 里压缩前完成、被摘要刻意漏掉 → 压后重查 |
| 帆布包 | 30 / 30 | 无差异，不动 | 幕 7"不用做"结局 |
| 围巾 | 系统 8 / 实物 2 | 差 6 > 3，**挂起** | 幕 7"做不了"结局 |

保温杯（47，贴着线下）和马克杯（52，贴着线上）是刻意的一对：
阈值两侧各站一个，规则才有戏可演。

## 长程任务场景：八幕剧情（全书贯穿示例）

同一张任务单，两种命运：本章的 demo 演无轨迹的命运，04 的 demo 演轨迹的解法。
场景是常量，能力是变量。

| 幕 | 剧情 | 本章 demo（无轨迹的命运） | 04 的 demo（轨迹的解法） |
|---|---|---|---|
| 1 领任务 | “处理一下今天的运营任务” | list_tasks → get_task(T-101) | 同一段，轨迹视角重看 |
| 2 先干起来 | agent 没查规则就开补 | 保温杯 → 50 落库 | 副作用 #1；rewind 后摘要带账本 |
| 3 用户纠偏 | “等等，先查补货规则，回到刚才” | **只能往前追加**，走错的几轮永远留在上下文里 | branch + branch_with_summary，抛弃段留遗言 |
| 4 规则路线 | search_rules → 逐项处理 | 玻璃杯补 20；马克杯超限报备**被拒**；保温壶补 20 | 同，审批事件进轨迹 |
| 5 换单 | “继续，处理盘点差异” | 雨伞按实物调 13 | 同 |
| 6 压缩 | “上下文有点长了，压一下” | 不演（打印“上下文只增不减”的事实） | compact 命令 → 摘要 + compaction entry，投影前后对照 |
| 7 继续 | “继续” | 帆布包不动、围巾挂起，正常干完 | 压后继续：重查雨伞（摘要漏了）→ 不重做已完成的 |
| 8 崩一刀 | 旁白：进程挂了 | 不演（resume 的解法归 04） | resume 恢复出“压缩视图 + 占位”，接着干 |

### 三个刻意的设计决定

**1. 进度住在会话里。**
任务单只读、没有状态字段，"做到哪了"只存在于对话里。
理由直白：这正是 04 压缩要保的东西——一旦有状态文件，agent 压完重读状态就行，
摘要的职责就被架空了，压缩的演示不成立。
简化是刻意的，书里如实声明。

**2. 写操作全部设值语义。**
"补到 50"写的就是 50，不是"加 47"。
rewind / 重放 / 压后重查，任何一次重做都不会把副作用叠上去——
"rewind 不回滚副作用"这个 04 的教学点才能安全地演。

**3. 摘要刻意有损。**
04 的 ScriptedSummarizer 摘要文本会故意漏掉雨伞的"已处理"：
保留窗里还有 T-102 的条目清单，模型对不上账，回头重查一次，发现已是 13，无害收场。
把压缩的代价（一次冗余查询）和收益（整段窗口）同时演出来，不演完美童话。

### 手动压缩：形状本章锁定，机制归 04

```text
触发  compact_request 控制事件（旁路，同 interrupt 的待遇），step 边界生效——
      流中间不换上下文，在飞请求的视图不漂移
动作  Summarizer.summarize(被压段) → summary
      刀口 keep_from_id = 保留窗第一条 user entry（刀口天然落在 turn 边界）
      保留窗 = 最近 2 轮（demo 用小值；真值是策略，归 05）
      traj.append(COMPACTION, {summary, keep_from_id, reason: "manual"})
投影  04 已有的语义一字不改：刀口前跳过、摘要插最前、只认第一刀
摘要  两档：ScriptedSummarizer（离线确定性，含"刻意漏掉雨伞"的剧本）
      / LiveSummarizer（裸 chat、不带工具、max_tokens 封顶）
```

被压段的输入是投影视图里的消息（含幕 3 branch_summary 的 `<summary>`）——
"摘要吞摘要"在这里第一次自然发生；
多刀互吞、认最后一刀的滚动折叠仍归 05。

## 下一章预告

任务能做了，会话却长出了三个新问题，而且幕幕都演过了：

- **试错回不去**（幕 3）：想换个思路，只能往前追加，走错的几轮永远占着上下文；

- **崩了全丢**（幕 8）：EventLog 记得住发生过什么，却读不回"我是谁、上次聊到哪"。

04（轨迹）接手：会话立成 append-only 的 entry 树，rewind 是移指针，
压缩是追加的视图标记，恢复是投影的收口。
