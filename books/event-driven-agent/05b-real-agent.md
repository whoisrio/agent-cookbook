# Stage 5b：真知识库——把"假检索"换成真的（05b-real-agent.md，设计已落地，代码见 src/baby_event_driven_agent/stages/stage05b_real_agent/）

（定位同 3c：场景升级章，不是机制章。05 与 06 之间的能力台阶——进入 rubric
之前，agent 得先是一个接近真实的运营助手：规则检索接真知识库，知识库构建
有管道。agent / 总线 / 轨迹层继续共享 04 的实现，新包只落知识层与工具后端。）

## 需求：逐行匹配接不住真实运营问答

Stage 1 起 search_rules 就是"逐行子串匹配"，正文里一直如实标注"不是真 RAG"。
对单文件几行规则够用；真实运营的知识是**多篇文档**（补货制度、盘点差异处理、
报销流程、会议室预订，每篇几十段），逐行匹配三个接不住：

1. **问题不会用关键词问**。用户问"同事垫付的打车钱怎么报销"，规则行里写的是
  "报销：报销流程：发起申请 -> 财务审核 -> 打款"——没有"垫付"两个字，
   词面匹配全盲。语义检索接的就是同义改写。
2. **答案没有来源**。逐行匹配返回裸文本，模型答"超 50 要报备"说不出依据是
   哪份制度哪一节——06 要评"准确"，得先有"依据"可指。
3. **知识运营没有闭环**。改一条规则只能手改文件；真知识库是：文档是源、
   索引是物化产物，写路径要能同步索引。

## 机制设计

### 1. 知识库文档层（data/knowledge/*.md）

运营手册拆成多篇 markdown：补货制度 / 盘点差异处理 / 报销流程 / 会议室预订 /
门店 FAQ。两条约束：

- 规则内容与 04 的 rules.txt **同一条线**（超 50 报备、差异 3 件内自调）——
  3c 八幕剧情的语义不断，马克杯报备被拒在知识库里同样成立；
- 每篇按 `# 文档标题` + `## 节标题` 组织，正文写足常识性段落（审批链、时限、
  常见问题）——让"切块"和"同义改写"有真实素材可演。

### 2. 构建管道（知识库构建）

文档 → 切块 → 索引，三步：

- **切块**：按 `##` 标题切节；超过长度上限的节按空行段落续切
  （块内文本格式 `文档标题 §节标题：正文`，超长节续块只含段落）。
  每块带来源元数据（源文件 / 文档标题 / 节标题）——检索结果能指回出处。
- **块 id**：内容派生（哈希），同一批文档两次构建块 id 完全一致——
  确定性用离线测试钉死，这是"检索命中可判定"的前提。
- **索引**：块的物化产物，JSON 落盘（版本号 + 块列表 + 嵌入模型名）。
  每块存：文本、词面倒排（字符二元组）、嵌入向量（可选）。可全量重建、
  可按文档增量更新（重切该文档的块、原地替换）。**文档是源，索引永远
  可重建**——换嵌入模型也是重建，不迁移；与"history 是 log 的投影"
  同一个形状：派生物可重算，源只有一个。

### 3. 检索双路（search_rules 后端替换）

工具名和 schema 基本不变（加可选 top_k），后端从逐行匹配换成知识库 top-k：

- **语义路（默认）**：块向量与查询向量 cosine，OpenAI 兼容 /v1/embeddings
  （配置同 RealLLM：仓库根 .env；嵌入模型独立配置，默认 bge-m3，
  本地 ollama 已验证可用）。
- **词面路（兜底）**：字符二元组 + IDF 加权重叠。嵌入端点不可用 / 未配嵌入
  模型时自动降级——检索契约不变，降级不是静默的：结果里如实标注
  mode（semantic / lexical），诚实纪律沿袭 05 的 fail-open。
- **返回格式**：每块一行 `[n] (来源：补货制度 §报备线，score 0.83) 正文`。
  无命中如实返回（不硬凑）——"检索没查到"本身是模型该知道的真事实。

### 4. 写路径闭环（update_rules 升级）

按标题写知识库文档（设值语义：重写整篇，与 update_inventory 同一纪律）→
重切该文档的块 → 原地更新索引 → 立即可检索。demo 演完整环：
运营说"把 XX 记进制度" → 写入 → 检索命中新规则。

### 5. 数据隔离（沿用 04 纪律）

docs 目录与 index 路径都是模块级 Path，测试与 demo 换工作目录副本，
包自带 data/（含 knowledge/）一个字节不动。

## demo 设计（四段）

1. **01-build-index**：构建管道——列文档、块数、节标题；连续构建两次，
   块 id 逐字节一致（确定性看得见）；索引文件落盘。
2. **02-search-upgrade**：同义改写对照——"同事垫付的打车钱怎么报销"，
   旧逐行匹配（04 的实现）无命中，知识库命中报销流程块并给出出处与分数；
   顺带展示 mode（嵌入不可用时如实标注词面路）。
3. **03-agent-with-kb**（真模型）：问"马克杯要补 80 件能直接补吗"——
   agent 调 search_rules 拿到报备线与审批链，回答带依据。
4. **04-write-back**（真模型）："把'盘点差异挂起需店长和财务双签'记进制度"
   → update_rules → 检索命中新规则——知识运营闭环。

## 测试设计

- **离线（确定性，不依赖模型）**：切块（标题切节 / 超长续切 / 元数据完整）、
  块 id 与索引重建一致、词面检索命中预期块、update_rules 写回后立即可检索
  （新块在、旧块替换）、嵌入客户端异常时降级词面路、继承的六件套 schema 不变。
- **真模型（可选，.env 缺失即跳过）**：agent 回答引用报备规则出处；
  同义改写查询端到端命中。

## 关键论点

- **工具接口不变，能力升级**：模型侧看到的还是 search_rules / update_rules，
  换的是工具背后的世界。前面各章的机制（审批、治理、轨迹、压缩）一行不用动
  ——机制分层的收益验证。
- **检索质量从"猜"变成"可判定"**：知识库是已知集合，"这条查询应该命中哪一块"
  有确定答案——06 rubric"过程正确"维度的直接素材；录制 golden trajectory 时
  检索命中就是硬断言，eval 用例的天然来源。
- 文档是源，索引是物化产物：可重建、可增量、换模型重建——派生物永远可重算。

## 取舍与风险

- 教学库很小（个位数文档、几十块），不引入向量数据库 / 分页——JSON 索引够用；
  "检索要不要配分页"等真需求出现再上（与 3c 的"道具不提前搬"同一判据）。
- 重排（rerank）不做：bge-reranker 模型本地有，但 top-k + 出处对教学够了，
  留一句"何时需要 rerank"即可。
- 嵌入调用是构建期一次性成本（几十块 × 毫秒级），不做缓存层——索引文件
  本身就是缓存。
