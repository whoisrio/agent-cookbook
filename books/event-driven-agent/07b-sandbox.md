# Stage 7b：沙箱——不可信代码的执行边界（07b-sandbox.md，骨架）

## 需求：agent 会执行不可信的代码

1. **bash 类工具**：模型生成的是任意 shell 命令，一条 `rm -rf` 或者一段
   `curl | sh` 就是事故。7a 的命令安全检测是"判"，判总有漏——兜底要靠执行边界。
2. **批量大规模运行**：单机 demo 可以祈祷；每个会话一个 agent、
   每天跑千万次时，"不可信代码"是常态不是例外，隔离必须工程化、
   且易于销毁（会话结束，沙箱连同里面的一切一起消失）。

## 第一层：让 OS 替你把关——系统调用控制

沙箱的物理基础：进程想干任何事（开文件、发网络包、起进程、改权限）
都得过系统调用这一道门，内核是唯一的仲裁者。那就直接从仲裁点下手：

- **macOS Seatbelt**（`sandbox_init` + profile）：声明式白名单，
  进程只能做 profile 允许的操作。7a 的命令白名单执行就是靠它。
- **Linux seccomp-bpf**：给进程装一个 syscall 过滤器，
  白名单之外的系统调用直接 kill。
- **配套的资源控制**：rlimit（文件大小 / 进程数 / CPU 时间）、
  独立工作目录——文件隔离的进程级答案。

局限：粒度是"系统调用面"。拦得住 `rm -rf` 直删共享文件，
拦不住合法 syscall 干的坏事——一个合法的网络调用就能把数据外泄出去。
 syscall 过滤是**能力裁剪**，不是**边界**。要更硬的边界，得换个思路。

## 第二层：容器——OS 级隔离原语的组合拳

容器不是新内核，而是把内核既有的隔离原语打包：

- **namespace**：视图隔离——pid ns（看不到别的进程）、mnt ns（独立的
  文件系统视图，rootfs）、net ns（独立的网络栈）、user ns（uid 映射）。
  → 对应"文件隔离"和"网络隔离"。
- **cgroups**：配额——CPU、内存、IO 上限。→ "计算资源隔离"。
- **rootfs + capabilities 裁剪**：最小文件系统、去掉特权。
- **销毁**：删容器即删世界——"易于销毁"天然满足。

优点实打实：启动快（复用宿主内核，没有引导过程）、开销小、镜像生态成熟。

结构性弱点只有一个，但是是致命的：**共享宿主内核**。所有隔离都是
宿主内核"自觉"执行的——guest 里没有任何东西在监督内核自己。内核出一个
提权或逃逸 CVE，同一台宿主机上的所有容器一起遭殃。对"专门运行不可信代码"
的场景，这是把全部赌注押在宿主内核上；配置纪律（只跑可信镜像、最小权限）
弥补不了结构性弱点。

## 第三层：VM——把仲裁权从内核手里拿走

VM 的解法是换仲裁者：hypervisor 接管，guest 有**自己的内核**，
虚拟化一套完整的硬件。一台 VM 要虚拟化的东西：

- CPU 与内存（页表虚拟化，如 EPT）
- 中断控制器、时钟
- 完整的设备模型：磁盘、网卡、USB、显卡、声卡……
- 固件引导（BIOS/UEFI）

隔离边界确实硬了：逃逸 = hypervisor 漏洞，攻击面比操作系统内核小得多。
代价也实打实：秒级启动、GB 级内存、完整设备模拟——一个 agent 一个 VM，
太重，满足不了"批量大规模运行"的启动与密度需求。

## 哪些组件 agent 用不上？

把 VM 的组件清单逐项过一遍 agent 场景：

| VM 组件 | agent 场景需要吗 |
|---|---|
| 独立内核（硬隔离） | **要**——这是对容器弱点的直接回答 |
| 完整设备模型（USB/显卡/声卡） | 不要——只要磁盘、网卡、串口控制台 |
| 固件引导（BIOS/UEFI） | 不要——内核直接加载 |
| 大规模 CPU/内存 | 不要——1~2 vCPU、几百 MB 够跑一个 agent |
| 通用桌面体验 | 不要 |

结论：agent 需要的只是"VM 的隔离边界"，不需要"VM 的全部内容"。

## 第四层：microVM——只保留需要的 VM

裁剪后的 VM：**virtio-only 设备模型**（磁盘/网卡/串口，没有模拟硬件）、
**无固件**（宿主机直接加载内核）、内存 MB 级起步——换来毫秒~百毫秒级
启动（比容器慢一点，比 VM 快一到两个数量级），同时保住独立内核。

- **Firecracker**（AWS Lambda/Fargate 底座）、QEMU microvm、cloud-hypervisor。
- **快照**：VM 状态可序列化落盘、可恢复——冷启动成本进一步摊销，
  环境预热一次、每个会话从快照恢复。
- 每会话一个 microVM + 会话结束销毁——"易于销毁"回到了粒度最小的单位。

四层对照：

| 层 | 仲裁者 | 隔离边界 | 启动 | 典型开销 |
|---|---|---|---|---|
| seccomp/Seatbelt | 宿主内核 | syscall 面 | 0 | ~0 |
| 容器 | 宿主内核 | namespace 边界 | 快 | 小 |
| VM | hypervisor | 硬件虚拟化 | 秒级 | 大 |
| microVM | hypervisor | 硬件虚拟化（裁剪） | 毫秒~百毫秒 | 小 |

## 使用方式：谁进沙箱？

边界在哪一层（syscall / 容器 / VM）和隔离对象是谁（单次工具执行 vs
整个 agent 进程）是两个正交的问题，没有"哪层只能包谁"的规定，
主流搭配由生命周期粒度决定：

| 搭配 | 用法 |
|---|---|
| 第一层 × 单次工具执行 | 主流。每次 bash 调用 fork 一个被 profile 包住的短命进程，结束即释放（7a 命令白名单的执行方式） |
| 第一层 × 整个 agent | 少见。agent 要连模型 API、写 log，syscall 面太宽，白名单难维护 |
| 容器/microVM × 两者皆可 | 取决于状态与秘密放哪（见下） |

沙箱边界划在执行体上，持久状态与秘密必须划在沙箱外："log 是唯一真相、
append-only、审计红线（06）"决定事实层不能随沙箱销毁；密钥长期有效，
不可信执行环境不应与之共存。据此两种模式：

- **模式 A：工具执行进沙箱**（agent 本体留宿主机）。单机部署默认，
  本书 demo 的形态：log、总线天然就在宿主机。
- **模式 B：整个 agent 进沙箱**（生产主流）。loop 连同工具执行都跑在
  microVM 里，状态与秘密全部外置：
  - **session log 流出沙箱**：事件本来就"离开 agent 之后要走传输层"
    （3b 的异步分发 + QoS），这里只是把边界从跨进程放大到跨机器——
    log 流出到宿主机/采集服务，由宿主侧落盘（04 的落盘与位点在收集端）。
    沙箱本地盘是可丢弃的——销毁的前提是里面没有需要保留的东西。
  - **密钥不进沙箱**：.env 留在宿主机；模型 API 调用经宿主机出口代理
    鉴权，沙箱里要么没有凭据，要么只有短时最小凭据。

四层不是四选一，是叠着用：模式 B 下，沙箱内每次工具执行仍被
syscall 过滤罩住，整个 agent 被 microVM 边界罩住。

## 关键论点

- 沙箱设计的本质是**"把仲裁权交给哪一层"**：越往上边界越硬、启动越慢。
  每一层都是在修上一层的结构性弱点，而不是配置问题。
- 容器的弱点是结构性的（共享内核）：所有隔离由内核自己执行，
  内核失守则全部失守。运行不可信代码的场景不能押注在它身上。
- microVM 的存在证明了一件事：隔离边界和启动速度不是二选一——
  砍掉用不上的虚拟化内容，两者可以同时要。

## 遗留问题：如何支撑批量大规模的 agent 运行

microVM 解决了"单个沙箱够快够硬"，没解决"一万个会话怎么管"：
池化预热、快照分发、每会话生命周期与销毁、宿主机调度密度——
这是 7b 的收口问题，也是工程化部署（超出本书单机 demo 范围）的起点。
