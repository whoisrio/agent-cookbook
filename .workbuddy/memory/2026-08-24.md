## dsh/cordis 文档答疑：ctx.provide vs ctx.reflect.provide（源码核实）
- 用户问：为什么 Service 基类里写 `ctx.reflect.provide(...)`，形态 A（对象插件 apply）里写 `ctx.provide(...)`，俩 provide 是否不同。
- 核实结论（对照本地 `examples/dsh/cordis/node_modules/@deepseek-ai/cordis/src/` 源码 + tsx 实测）：
  - **同一个底层函数** `ReflectService.prototype.provide`。`ctx.provide` 是 ReflectService 构造时 `mixin('reflect', ['get','set','provide',...])`（reflect.ts:219）挂出的 accessor，get 时取 `ctx.reflect.provide` 并 bind 到 reflect（mixin 实现 reflect.ts:364-390）。每次访问重新 bind，故 `ctx.provide === ctx.reflect.provide` 为 false、name 是 "bound provide"——但 spy 测试证明调用 100% 转发到底层。
  - **不是"必须"而是"选择"**：实测非 Service 类插件构造期用 `ctx.provide` 门面照样挂牌；对象插件 apply 里用 `ctx.reflect.provide` 也照样生效。两路写进同一 store，可互换。
  - Service 基类写 `ctx.reflect.provide` 只是框架内部代码绕开门面直呼底层（service.ts:57）。
  - 时序澄清：Service 插件**没有绕过 ctx.plugin**。`ctx.plugin(WaterService)` → registry.resolve 返回类本身 → new Fiber → 依赖齐 → `_runner.execute` 检测 isConstructor → `new WaterService(ctx)` → 构造函数里 `ctx.reflect.provide('water', this)` 挂牌 → 再调 `[Service.init]`（fiber.ts:250-261）。provide 是"挂牌"动作，不是"注册"动作。
  - 文档 §2（dsh-extension-cordis-full-story.md）"二者都经 ctx.plugin() 受理"的说法正确，无需改；用户疑点来自"构造函数里看到 provide"误以为绕过注册管线。

## dsh/cordis 答疑续：wrapped/await/inertia + PowerService 占位名是多余的（源码+实测）
- wrapped 机制：`ctx.plugin` 返回 `Object.create(fiber)` + 自定义 then（registry.ts:331-335），委托 `fiber.await()`（fiber.ts:704 是 async，返回真 Promise）。fiber 无 then，不包装则 `await ctx.plugin()` 立即返回不等。async 会毁掉"对象+可等待"双身份，所以 plugin 不写 async。onFulfilled/onRejected 是引擎 new 内部 promise 时现造的决议函数，非 cordis/Fiber 类提供。
- inertia 三作用：防重入（_setEpoch 见 inertia 非空即 return，fiber.ts:629）、收尾接力（_reload/_unload 尾部对比 epoch 变了就续下一段过渡，667/692 行）、可等待（await()/dispose() 用 while 等链式过渡，705/293 行）。
- JS 单线程无锁；异步竞争靠"检查点 + epoch 复查"：_reload 入口 `await Promise.resolve()`（fiber.ts:650）是"决定与执行解耦"——同 tick 里 notify 链的后续变更落地进 epoch，恢复时复查不新鲜就跳过 apply（654 行）。
- **PowerService 占位名纯多余（用户问 check 方案时实测发现）**：Service 构造函数只在依赖齐后被执行（fiber inject 门禁：依赖没齐 PENDING，不 new 实例），所以直接 `super(ctx,'power')` 挂真名时 water 必然已齐，"依赖齐才挂牌"由 static inject 天然保证。占位名+[Service.init] 再 provide 是绕路。已改 `examples/dsh/cordis/coffeeshop/services.ts`（删占位名与 init，直接挂真名），tsx 跑通，行为与原版一致。
- **check 替代不了 inject（实测）**：`[Service.check]` 是消费者侧过滤（impl.check false → 消费者 _checkImpl 删依赖），但 notify 只按 inject 反查，check 里读的依赖变化不唤醒消费者（water 补挂不唤醒 inject ['power'] 的店）。分工：inject 管"依赖门禁"（可传播），check 管"自身可用性"（不传播，适合数据库连接这类常驻服务）。

## dsh/cordis 答疑续二：inject 依赖是"名字级"的 + coffee 首次激活作废案（实测+插桩定位）
- **inject 'coffee' 不等 coffee 开业**：'coffee' 是 floor apply 同步段 provide 的 fiber 引用（floor.ts:49），cordis 依赖检查（_checkImpl）只看"store 有没有名 + 提供者 fiber 活不活"，不看内容 ready 没 ready。且 PENDING 的 fiber 无 inertia，`await coffeeFiber` 立即返回（await() 只等进行中过渡，不等未来激活）。实测 bakery inject 'coffee' 立即开业。
- **bakery inject 'sell' 的现象真相**（用户改 floor.ts:22 后实测）：bakery 不是"不被激活"，是等到 [15:00] 咖啡店**第二次**激活才开业。插桩（Fiber uid 分配 + _reload 收尾 + internal/status）定位：
  - main.ts 被用户改成 power 先挂（34 行）、water 后挂（37 行）；main 是 async 一口气跑，[09:00] 咖啡店开始异步激活（apply 里 `await ctx.plugin(CleaningService)`），期间 main 已同步执行完 [14:00] `registry.delete(WaterService)` + [15:00] `ctx.plugin(WaterService)`（新 fiber uid 5→8），power 也因 water 退租被删（2->5）。
  - coffee 的 _reload 收尾（fiber.ts:1363-1369）复查 `epoch === oldEpoch`：old=":5:4"，new=INACTIVE（_store 里 power 没了、water 换成 uid8）→ **加载作废**，1->5（UNLOADING）→5->0→0->1 重新加载→1->2 这次稳定 ACTIVE→sell 重新 provide→notify(['sell'])→bakery 才开业。
  - 即"入口让出 + epoch 复查"机制真实表演：依赖在加载期间变化→加载作废重来。coffee 状态序列 0→1→5→0→1→2。
  - **样例时序缺陷**：main.ts 停业/复业段没等咖啡店首次激活完成（main.ts:34 await power 因 PENDING 立即返回，main 不等 coffee）。原版 bakery inject 'coffee' 不暴露（同步挂牌），改 inject 'sell' 后暴露。修复方向：main.ts 先等 internal/service('sell') 再动 water，或把 [14:00] 段放到 coffee 首次激活后。

## dsh/cordis coffeeshop：effect/dispose 看板从 getEffects 快照改为真实 NoticeBoard 对象（用户反馈"还是 log 而已"）
- 用户嫌上一版生命周期看板「还是 log 而已」，要求：假设有一个 ctx 持有的「公告牌」对象，服务 provide → 往里加信息、dispose → 移除；effect 的标签（招牌灯/行业报纸）保留为业务动作细节，但公告牌状态要可查。
- **实现（重写 common.ts）**：`ctx.board: NoticeBoard`（根上下文 `ctx.provide('board', new NoticeBoard())` 注入，declare module 合并进 Context）。NoticeBoard 是真实 Map 对象，按 `owner/kind/label` 记条目，`render()` 打印快照。三类条目：
  - **provide**：零侵入，靠 `internal/service` 事件驱动（value 有值→登记，undefined→注销），Service 子类一个字不用改；'board' 自身 skip。
  - **effect**：`trackEffect(ctx, owner, label, fn)` 包装 `ctx.effect`，注册时 `board.add`、dispose 时 `board.remove`（业务 logger 动作仍在 fn 内）。
  - **event**：`trackEvent(ctx, owner, eventName, handler)` 包装 `ctx.on`，订阅时 add、退订（含插件卸载自动 off）时 remove。
  - `installLifecycleBoard` 仍订阅 `internal/status` 打开业/停业标题，并在 UNLOADING 时 `board.removeOwner(fiber.name)`（静默，避免与 effect dispose 的 ▼ 重复打印）。新增 `renderBoard(ctx, title?)` 给 demo 做前后对比快照。
- 全插件适配：`coffee/cleaning/floor(bakery)/fridge/ac` 的裸 `ctx.effect(...)`→`trackEffect`、`ctx.on(...)`→`trackEvent`；demo 01/02/03 在关键时机 `renderBoard`（开业后 / 停水前后 / 卸载前后）。`settle()`（setTimeout 60ms）等 cordis 异步 dispose 跑完再 snapshot。
- 验证：`tsx` 跑 01/02/03 全过——公告牌开业 21 条、停水注销到 2 条（finance+meetingRoom，floor-manager 无 water 依赖故 meetingRoom 留）、卸载 fridge 从 21→18 条；`tsc --noEmit` coffeeshop/* 零错误（02/04/07 既有报错与本改动无关，未动）。
