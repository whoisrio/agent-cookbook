## 纠错：上一轮我对 Anthropic vs OpenAI 的判断有误

我上一轮说"Responses 只搬走了对话状态，Anthropic 连执行环境都搬走了、走得更远"——**这个判断是错的**。OpenAI 在 2026-02-11 就已经把 Responses API 扩成了 agent 平台，两者基本同步：

- **Server-side Compaction**：OpenAI 字段 `context_management: [{"type": "compaction", "compact_threshold": 200000}]`；另有独立端点 `/responses/compact`。Anthropic 是 `context_management.edits: [{"type":"compact_20260112", trigger:{...}}]`。**两家字段名都叫 context_management**，连设计都同构（阈值自动触发 + 独立端点/策略）。
- **Hosted Shell Containers**：Debian 12 + Python 3.11 / Node 22 / Java 17 / Go 1.23 / Ruby 3.1，持久存储在 `/mnt/data`，并行执行、输出按模型指定上限截断并保留头尾、网络策略可控。对应 Anthropic Managed Agents 的 environment + agent_toolset。
- **Skills 标准**：OpenAI 用 SKILL.md（YAML frontmatter + Markdown），与 Anthropic Agent Skills 竞争；差别是 OpenAI 绑自家云、Anthropic 主打可移植。
- 另有 WebSocket 模式（连接内缓存 previous response 状态）、Conversations API（持久化 conversation 对象，无 30 天 TTL，区别于 response 的 30 天）。

**真正的差异在 compaction item 的形态**：OpenAI 是加密不透明 token 表示（官方文档原话 "opaque and not intended to be human-interpretable"）；Anthropic 是明文 `<summary>` 块，还能用 `instructions` 参数整体替换默认摘要提示词。可审计性 vs token 效率。

**memory 必须分清两套**（都叫 memory，性质相反）：
- Anthropic Messages API memory tool（`{"type":"memory_20250818","name":"memory"}`）是**客户端侧协议**，Anthropic 不代存任何数据，开发者自己实现 view/create/str_replace/insert/delete/rename 六条命令。不是 memory 服务。
- Anthropic Managed Agents 的 agent memory 才是服务端托管（beta header `agent-memory-2026-07-22`）。
- OpenAI 侧的 Memory 出现在 Agents SDK 的 capabilities 里（Filesystem / Shell / Compaction / Memory / Skills，2026-04-15 发布，deepsense 二手博客来源，待核实）与 ChatGPT 产品的 Dreaming V3；Responses API 字段层面未见对等物。

**三件套联动（视频主线最有价值的一段）**：context editing 清除旧工具结果前会先给模型一个自动警告，让它在被清除前把重要信息写进 memory 文件——先落盘再擦除。分工：context editing 丢噪音，compaction 压全量，memory 存跨会话精华。

## 纠错二：compaction 与 prompt caching 并不是"天然打架"（2026-09-02 查官方文档）

我上一轮推断"压缩会破坏缓存前缀，两者天然冲突"——官方 Compaction 页有专门的 Prompt caching 小节，明确说两者配合良好：

- 可以在返回的 `compaction` block 上直接加 `cache_control: {type: "ephemeral"}` 断点缓存摘要本身。
- 建议在 system prompt 末尾单独加一个 cache 断点，这样压缩发生时 system prompt 的缓存不失效，只需把摘要写成新的 cache entry。
- 被压缩掉的原文确实会失效，但那部分本来就是要丢弃的内容，不算损失。

结论：冲突存在但被官方设计吸收了，不能当成一个"未解缺陷"讲。

## compaction 三层模型（回答用户"是不是靠 user message 触发"）

用户反问"不是直接通过 user_message 操作的么"。核实后结论：**我说的窄了，用户记的层级不同**。三层并存：

1. **API 层（服务端）**：`context_management.edits: [{type: "compact_20260112"}]` + beta `compact-2026-01-12`。官方参数表：**`input_tokens` 是唯一支持的 trigger 类型**，value 下限 50,000，默认 150,000。全篇 11 个章节，没有任何 manual / client-side compaction 章节，也没有通过特殊 user message 强制触发的开关。
2. **客户端层**：自己发一条 user message 让模型总结，再替换 messages。LangGraph 的 summarization 节点、各类 cookbook 都在这层。
3. **产品层**：Claude Code 的 `/compact [instructions]`、`/autocompact`、`/rewind` 的 summarize。是用户敲命令，客户端拼成 user message——确实是 user message，但那是 Claude Code 的实现，不是 API 能力。

注：OpenAI 侧有独立端点 `/responses/compact` 可手动触发，Anthropic 侧没有对等物。

## 官方 Current limitations（视频可用素材，两个真实的坑）

- **摘要模型不可选**：只能用请求里指定的同一个模型做摘要，没法换成便宜模型降本。（推论：某第三方博客写的 `compaction_control={"model": "claude-haiku-4-5"}` 是编的，不要引用。）
- **定义 tools 时压缩可能静默失败**：模型在内部摘要步骤里偶尔会去调工具而不是写摘要，此时返回 `compaction` block 但 `content: null`。官方规避办法是在 `instructions` 里显式写 "Do not call any tools while writing this summary; respond with text only"。
- **计费陷阱**：`usage.iterations` 会多一条 `type: "compaction"` 记录，顶层 `input_tokens`/`output_tokens` **不含** compaction 迭代。用旧逻辑做成本统计会严重低估（实测示例：顶层报 23,000，实际处理 203,000）。Bedrock 文档也特别提示要改统计逻辑。
- 附带事实：`/v1/messages/count_tokens` 会 apply 已有的 compaction block 但不会触发新的压缩。

## 开源 provider / 推理服务是否支持服务端压缩（2026-09-02 核实，结论：全部不支持）

用户问"压缩这个能力开源 provider 的 API 有支持的么"。逐个查官方文档，答案是**没有一家**，且缺失有结构性原因。

逐家核实结果：
- **vLLM**：支持 Responses API（`/v1/responses`、`/{id}`、`/{id}/cancel`）、Chat Completions；有 `/v1/messages`（LlamaStack 文档把 vLLM 列为 passthrough 原生支持方）。store 需 `VLLM_ENABLE_RESPONSES_API_STORE=1` 显式开启。功能清单无 compaction / context_management。
- **SGLang**：`/v1/messages` 默认注册、无需额外 flag，支持流式、工具调用、`count_tokens`。无压缩。**决定性反证**：SGLang 的 GLM-5.3 / Claude Code 集成文档让用户设 `CLAUDE_CODE_AUTO_COMPACT_WINDOW=1000000` —— 压缩窗口是 Claude Code 的**客户端环境变量**，服务端完全不参与。
- **llama.cpp**：原生 `/v1/messages` + `/v1/messages/count_tokens`（PR #17570，2026-01 前后，ggml-org 官方博客）。功能清单：流式、工具调用、视觉、extended thinking。**无 compaction、无 cache_control**。
- **Ollama**：`/v1/messages` 兼容性文档有明确 "Not supported" 表：`count_tokens`、`tool_choice`、`metadata`、**prompt caching (cache_control)**、Batches、Citations、PDF、SSE errors。compaction 连"不支持列表"都没进——压根不在协议覆盖范围内。
- **Llama Stack（OGX）**：Anthropic Messages adapter，passthrough（Ollama / vLLM）或翻译模式。已实现清单不含压缩，"Not yet implemented" 只列了 Message Batches。
- **网关层（LiteLLM / Bifrost）**：做的是路由、failover、语义缓存、预算治理、MCP Gateway。**都没有 compaction**。
- **开源权重模型厂商（DeepSeek / Qwen / Kimi / GLM / MiniMax）**：API 只做 OpenAI/Anthropic 协议兼容的传输层，未见 `context_management` 对等物。第三方对比文档提到 DeepSeek-V3.2、Kimi K2.5/K2.6 有"超阈值丢弃最早工具结果"策略，但那是其 **agent CLI 层**行为，不是 API 能力（二手来源，未采信）。

**为什么开源侧做不出来（比"有没有"更值得讲）**：
1. 压缩不是推理问题，是编排问题——要服务端持有会话状态 + 额外跑一次采样 + 把结果拼接回上下文。开源推理引擎刻意做成无状态 token 生成器。
2. **摘要提示词天然绑定模型**。Anthropic 官方文档原话"default summarization prompt varies by model"。厂商能发默认值是因为它拥有模型；vLLM 服务 100+ 架构，通用摘要提示词在半数模型上是垃圾。这个能力结构上属于"拥有模型的那一方"。
3. 依赖下层缓存。Ollama 连 `cache_control` 都不支持，压缩是更上面的一层。
4. 经济账：压缩多一次采样、按主模型价格计费。商业 API 那是毛利故事，自部署就是自己掏钱，用户宁可自己控制。

**反向论证（会不会有人做）**：会。embeddedllm/vllm-responses 这类 Responses 网关（OpenAI Responses 规范 ↔ vLLM 的翻译层，带 ResponseStore 数据库 + 内置工具 + MCP）一旦有了状态存储，加压缩大概两百行。所以不是"开源做不到"，是"还没人需要"——因为客户端全自己做了。

**客户端层确实全都自己做了**（同一份第三方对比文档）：Gemini CLI 50% 阈值四阶段、Goose 80%、Kimi CLI 85% 且递归分割摘要最多 3 层、Qwen Code 70% / warn-auto-hard 三档 ladder、Copilot CLI、Codex CLI、Aider。**阈值从 50% 到 92% 全不一样**。

**给视频的 punchline**：服务端压缩真正的价值不是"帮你省了写代码"，而是**标准化了一件目前每个 agent 答案都不同的事**。

## 关键纠错三：服务端压缩【不是】Claude Code 的默认机制（2026-09-02 核实）

用户问"这个上下文服务端压缩是 claude code 现在的默认机制么"。答案：**不是，恰恰相反。Claude Code 的压缩是纯客户端的，跟 `compact_20260112` 是两条平行赛道。**

**硬证据（官方文档原话）**：
- 官方 Claude Code 文档 code.claude.com/docs/en/context-window：「When a long session compacts, **Claude Code summarizes the conversation history**」；「As of v2.1.198, **the summarization request** inherits your session's extended thinking configuration」——主语是 Claude Code，它自己发摘要请求。
- 官方 Agent SDK 文档 code.claude.com/docs/en/agent-sdk/agent-loop：压缩时 SDK 发出 `type: "system", subtype: "compact_boundary"` 消息（Python=SystemMessage，TS=SDKCompactBoundaryMessage）。**这是 Claude Code 自己的消息类型，不是 API 的 compaction block。** 另有 `PreCompact` hook，trigger 字段为 manual/auto，可在压缩前归档完整 transcript——服务端压缩没有这个钩子点。
- LiteLLM 官方文档明确区分两条路：一是对 `context_management` 的透传/polyfill；二是「请求**不**含 compact_20260112 编辑，但消息历史里已有 compaction 块（例如来自之前的 **Claude Code 客户端压缩**）」时的仅切片转发。→ 证明 Claude Code 产出的 compaction 块是客户端生成的。

**Claude Code 客户端的多级流水线**（逆向源码，多家一致，但非官方文档）：
1. Microcompact（每轮前）：缓存热 → 走 `cache_edits`，**在服务端缓存前缀里删旧工具结果，本地消息一个字节不动**（保住 transcript + 缓存命中）；缓存冷（距上条 assistant 消息 >60 分钟，Anthropic cache TTL 约 1 小时）→ 本地替换成 `[Old tool result content cleared]`。可压缩工具白名单：Read/Bash/Grep/Glob/WebSearch/WebFetch/Edit/Write；Agent、用户消息、助手分析文本**不压缩**。
2. Session memory compaction：后台 fork 子 agent 持续维护记忆文件，压缩时直接复用，**零额外 API 调用**；需保 tool_use/tool_result 配对、thinking block 完整。
3. Full compaction（兜底）：自己发摘要请求，9 段式结构化摘要（Primary Request / Key Concepts / Files / Errors / Problem Solving / All User Messages / Pending Tasks / Current Work / Next Step）。`NO_TOOLS_PREAMBLE` 是因为 4.6 模型在摘要任务里调工具失败率 2.79%（4.5 只有 0.01%）。
4. PTL 重试：压缩请求本身超长时按 API round 分组丢最旧的组，最多 3 次。
5. 断路器：连续失败 3 次后该 session 永久停用 auto-compact。
- 压缩后 re-injection：重读最近 5 个文件（总量 5 万 token、每文件 5K 上限）、skill body（25K 上限）、plan、MCP 指令。
- 阈值：`effective_window = context_window - 20K`，触发点 `effective_window - 13K`。1M 窗口模型官方说约 967K。**我上一轮说的"92%"来自逆向博客，版本相关，别当定论。**

**为什么不用服务端压缩（最有料的四层原因）**：
1. **可移植性**：Claude Code 跑在 Bedrock / Vertex / LLM 网关 / 自定义模型 ID 上，一个 Anthropic 专有的 beta header 覆盖不了。
2. **模型覆盖**：compaction 只支持部分模型（文档列 Opus 4.6；第三方说 Haiku 4.5 不支持），而 Claude Code 要支持多种模型。
3. **可控性**：服务端只给一个 `instructions` 字段；客户端却有 `/compact focus`、CLAUDE.md 里的 summary instructions、PreCompact hook、9 段式模板。
4. **完整性**：客户端压缩保住本地 JSONL transcript（/rewind、resume、审计）；服务端压缩把历史换成一块必须原样回传、自己不拥有的块。

**视频角度升级**：厂商自己的旗舰 agent 产品没有用自己的服务端压缩 API。这不是"还没迁移"，是产品团队和 API 团队对同一个问题的两套答案同时在跑。比"讲 API 参数"值钱得多。

**待核实**：`cache_edits` 这个 API 名只出现在逆向源码解读里，官方文档我没找到（可能是 Anthropic 给自家产品的私有 beta）。视频里若要讲，标成"逆向所得"。

## 转向：视频结构定为「A 家 API 约束 → agent loop 设计」（2026-09-02 下午）

用户拍板：不再讨论服务端压缩（他判定无价值，倾向旁路小模型 + 客户端自控范围）。改成「A 家 API 只讲独特逻辑（字段差异一句话带过）→ 引申到如何基于 API 设计 agent-loop」。

**我对用户两处判断的反驳（已核实）**：
1. "服务端压缩没价值"结论对，理由不够硬。它唯一不可复制的价值是**原子性**（压缩与本轮同一 request，无竞态、无摘要请求失败分支）；但这个保证被自己的静默失败吃掉了。真正的理由是**压缩是 policy 不是 mechanism**，policy 属于应用。
2. **"旁路小模型"有硬天花板**：Haiku/Sonnet 200K 窗口 vs Opus 500K–1M，大上下文小模型物理装不下。适用域要拆：小上下文成立（摘要请求读全量历史，几乎吃不到缓存，给便宜模型是纯省）；大上下文必须**趁早压 + 分段递归**（社区把 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 从默认 95 调到 50 的真实理由不是省 token，是让上下文永远停在压得动的尺寸）。**坑**：主会话里 `/model haiku` 再压是陷阱——切模型烧掉累积的 Opus 缓存，新模型重读全历史反而更贵。所以"旁路"必须是独立 session / 独立 provider 的旁路请求。Claude Code 默认主模型压（摘要请求继承 extended thinking 配置），小模型旁路是**省钱优化不是架构正解**。

**新核实的官方事实（视频素材）**：
- **thinking block**：工具调用时必须完整回传，不传就报错；连续 thinking 块序列不可重排/修改；`signature` 加密承载完整思考，`display: omitted` 时文本为空但签名仍在；改 thinking 参数（开关或 budget）会使 **messages 缓存失效**，但 tools / system 缓存不受影响。Opus 4.5+ / Sonnet 4.6+ 默认保留历史 thinking 块，早期模型与 Haiku 会剥离。
- **prompt caching**：最多 4 个显式断点（自动缓存也占 1 个槽，4 个占满再开自动缓存返回 400）；最小可缓存 4096 tokens（Opus 4.5+/4.6/4.7、Haiku 4.5）或 1024（Sonnet 4.5/4.6），不足不报错只是静默不缓存；TTL 默认 5m，可选 1h（写入 2× 价，5m 是 1.25×），1h 必须排在 5m 之前；前缀顺序 **tools → system → messages**，改工具定义全层失效；断点应放在"跨请求保持不变的最后一块"。
- **stop_reason 七值**：end_turn / max_tokens / stop_sequence / tool_use / pause_turn / refusal / model_context_window_exceeded。`pause_turn` = 服务端工具的服务端采样循环达迭代上限（默认 10），处理方法是把 `response.content` 原样作为 assistant 消息再发一次（客户端 tool_use 停下来时 stop_reason 是 tool_use，不是 pause_turn）。`refusal` 是 **HTTP 200 不是错误**，带 `stop_details.category`；Fable 5 可用 `server-side-fallback-2026-06-01` 自动换模型重跑，并有 fallback credit 避免付两次缓存钱。
- **工具结果上限（官方数字）**：Anthropic engineering 博客《Writing effective tools for agents》原话「For Claude Code, we restrict tool responses to **25,000 tokens** by default」，官方建议 pagination / range / filtering / truncation with sensible defaults。
- **PARTIAL 契约（真实 bug 案例）**：Claude Code v2.1.145（2026-05-19）把 Read 的超限返回从硬报错改成截断前缀 + PARTIAL 提示。教训：标记放**尾部**会被模型当注释忽略，模型把前缀当完整文件，未读部分的规则静默丢失（anthropics/claude-code#28783）。标记必须放开头 banner 或独立结构化字段。三件套缺一不可：有用前缀 + 结构上独立的标记 + 续读句柄（offset/cursor）。
- **清旧的硬约束**：prune 时只能替换 tool_result 的 body，**不能删 tool_result 结构本身**——API 会校验 tool_use / tool_result 配对，删了直接报错。请求体约 32MB 上限（第三方观察值，官方会变），图片型 tool_result 会悄悄累积逼近。
- `response.content` 必须整体 append，只取 text 会让 compaction block 与 thinking block 静默丢失。

**我给出的结构主张**：粘合剂不是"讲完 API 再讲 loop"，而是「API 约束 → loop 形态」的因果链。只挑三条 A 家独有约束：① thinking 块带签名 → messages 是块链不是数组，裁剪必须认签名；② 4 个缓存断点 + 改 tools 全失效 → loop 只能 append-only，头部冻结；③ 服务端工具吃掉执行权 → 执行不全是本地函数，多出 pause_turn 要接住。

**loop 七层分层（我提的模型）**：前四层主循环体（每轮跑）：组装（system 动静分离/工具集冻结/append·insert·prune）、调用（thinking 预算/流式分块/response.content 整体保存）、决策（stop_reason 七值分派）、执行（环境/结果上限/PARTIAL 契约/错误回灌不抛）；后三层旁路守卫（不每轮触发）：收敛（迭代上限/token 预算/连续失败断电）、压缩（时机/范围/旁路模型/rewind 兜底）、持久化（transcript 落盘/checkpoint/resume·fork）。

**已产出（2026-09-02 17:0x）**：`books/从 Messages 到 Agent Loop.md`（361 行 / 约 1.96 万字符，对照篇 657 行，符合用户"不用那么详细"的要求）。结构：开头 hook（anthropic-version 三年没动 + beta header 堆版本）→ 一、与 OpenAI 同构部分一句带过 + 字段差异清单 → 二、三条会改变代码形状的约束（thinking 签名块链 / 显式缓存断点 4 个且改 tools 全炸 / 服务端工具吃掉执行权引出 pause_turn）→ 三、七层 loop（组装·调用·决策·执行 为主循环体，收敛·压缩·持久化 为旁路守卫）→ 四、代价与局限。

## 关键纠错四：prompt caching 不是"必须手动标断点"，我上一段结论整个过期（2026-09-02 晚，用户质疑后核实）

用户反问"a家api要求手动打cache标记，你的说法几乎是要求开发者必须自行控制，你确定是这样的么"——**用户是对的，我错了，而且错得比他问的更多**。官方 2026 年连发三刀，把我文章里那条"约束二"的推论整个拆掉了：

1. **Automatic caching，2026-02-19 GA**（官方 release notes 原话）：请求体顶层加一个 `cache_control: {"type": "ephemeral"}`，系统自动把断点放在最后一个可缓存块，**"moving the cache point forward as conversations grow. No manual breakpoint management required."** 与 OpenAI 的差别从"手动 vs 自动"缩小成"声明一次 vs 零声明"（OpenAI 是零配置，够 1024 token 自动命中）。
2. **Mid-conversation tool changes，beta header `mid-conversation-tool-changes-2026-07-01`**（随 Opus 5 于 2026-07-24 发布）：`tool_addition` / `tool_removal` 块放在 `role: "system"` 消息的 content 里，引用预先声明在 `tools` 里的工具（`tool_reference` / `mcp_tool_reference` / `mcp_toolset_reference`）。**`tools` 数组本身不变 → 缓存前缀 byte-identical → 不失效**。可用模型：Fable 5 / Mythos 5 / Opus 4.8 / Opus 5（**Sonnet 5 不支持**）。→ 直接推翻我"整个 session 必须冻结 tools 数组"的结论。
3. **Mid-conversation system messages**（**无需 beta header**，同样只在 Fable 5 / Mythos 5 / Opus 4.8 / Opus 5，Sonnet 5 不支持）：在 messages 中间插 `{"role": "system"}` 加中途约束，不破坏前缀缓存。改顶层 `system` 字段则会让整个前缀 hash 变掉。
4. **Cache diagnostics，beta header `cache-diagnosis-2026-04-07`**：传 `diagnostics.previous_message_id`（首轮传 null opt-in），返回 `diagnostics.cache_miss_reason.type`：`model_changed` / `system_changed` / `tools_changed` / `messages_changed` / `previous_message_not_found` / `unavailable`，`*_changed` 还带 `cache_missed_input_tokens`（量级指示，非计费值）。→ 推翻我"缓存没命中不报错、只能看着零"的论断。官方特别说明：**diagnostics 答"请求变了没"，`usage.cache_read_input_tokens` 答"缓存命中没"**，两者结合才能区分"请求写错"与"条目过期"。

**顺带核到的新事实（都已写进文章）**：
- **`tools_changed` 的非确定性序列化坑**：官方原因含"tool input_schema JSON 序列化不确定"。Python dict 不带 `sort_keys=True` 时，两个结构相同的请求 hash 不同 → 全程没改工具却一直付全价写入。
- **prefill 在 A 家多数新模型上直接 400**：Fable 5 / Mythos 5 / Mythos Preview / Opus 4.8 / 4.7 / 4.6 / Sonnet 4.6 不支持 prefilling assistant messages，`Prefilling assistant messages is not supported for this model`。替代是 `output_config.format` 结构化输出。→ 这是"从 OpenAI 迁移过来必踩"的坑。
- **thinking 块 400 的准确形式**：thinking / `redacted_thinking` 块被编辑/重排/过滤/重构 → 400，错误消息带位置如 `messages.1.content.0`；**每个块都必须原样回传，包括 `thinking` 字段为空的**。
- **stop_reason 实际是 8 个值**：handling-stop-reasons 指南列 7 个（end_turn / max_tokens / stop_sequence / tool_use / pause_turn / refusal / model_context_window_exceeded），API reference 另列 `compaction`。`refusal` 确为 **HTTP 200 非错误**，且 **pre-output refusal 的 `content` 数组是空的** → 必须先查 stop_reason 再读 content。`pause_turn` 迭代上限默认 10。
- **`server-side-fallback-2026-06-01`** 有 fallback credit 机制：`usage.fallback_credit`，`beta_fallback_credit_redeemed` 表示重试按"整段对话一直在重试模型上"重算（含缓存）。
- `deferLoading` 是 **Vercel AI SDK 的 Anthropic provider 提供的**，不是 Anthropic API 字段；配合 `tool_addition` 让工具在被唤起前不占上下文。

**新题眼（已用于重写版文章的主线）**：Anthropic 同一年同一方向，caching 收成了、compaction 没收成，分界线是 **mechanism 能收进服务端，policy 收不了**。caching 三刀（自动断点 / 绕过限制 / 可观测）每一步都没拿走控制权；compaction 塞给用户一个改不了的默认值且静默失败。判断任何"厂商又替你做了一件事"的通用问法：**这件事里有没有只有你知道的信息**。
