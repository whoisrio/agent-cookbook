## 修 baby_event_driven_agent 的两个 steering bug（红-绿走完）

用户授权"先把 bug 修了"，修的是昨天（09-07）实测坐实的那两个。新建
`src/baby_event_driven_agent/tests/test_agent_loop.py`，先写测试跑红、再改、再跑绿。

1. **end_reason 被 steering 污染成 None**（agent.py `_run_turn` 的 except StepInterrupted）
   根因：`_after_interrupt` 返回值兼职两种意思（None=本轮继续 / 字符串=结束原因），
   调用方直接 `end_reason = await ...`，steering 的 None 就一直留到本轮收尾把 stop 顶掉。
   修法：改用局部变量 `stop` 接，只有真要结束才写进 `end_reason`。没有动 `_after_interrupt`
   的返回契约（那属于设计改动，没授权）。
2. **空闲时收到的控制类事件不进轨迹**（`_handle` 的 USER_STEERING / INTERRUPT 两个分支）
   两个分支都补 `self._trajectory.append(event)`。不写的话 `replay_messages` 重建不出
   空闲时的 steering（`_drain_steering` 里是有 append 的，就 `_handle` 里漏了，不对称）。

验证：新增 2 个用例，13 passed（11 原有 + 2 新增），demo 无回归
（demo 最后一段 approval_gate 注入 steering 的场景 `turn.end end_reason=stop` 正常）。

**没修的**：被取消的 step 只有 `model.before` 没有 `model.after`，轨迹表达不出

## 调研 hermes-agent 的事件驱动 / agent loop（供 baby_event_driven_agent 对照）

源码 `/Users/rio/repos/opensource-refs/hermes-agent`。结论：**hermes 没有"事件驱动的
agent loop"**，是「外层事件驱动调度 + 内层同步 while 迭代」。仓库里 grep
EventBus / publish / subscribe / dispatch_event 零命中，不存在事件总线。

- **内层循环**：`agent/conversation_loop.py:1484`
  `while (s.api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) or agent._budget_grace_call:`
  阶段推进靠 `_run_phase(fn, agent, s)`（:1342，按签名反射取参数、把 verdict 字段写回
  dataclass state）。工具结果是**函数返回值**回循环，不是事件队列。
- **外层事件**：`MessageEvent`（`gateway/platforms/event.py:36`，dataclass，有
  `internal` 标记合成事件）。所有来源都收敛到 `adapter.handle_message(event)`
  （`gateway/platforms/base.py:3479`）→ `_start_session_processing`(:3391) →
  `asyncio.create_task(_process_message_background)`(:3398) → `_message_handler` →
  `gateway/run_inbound.py:1179` → `_handle_message_with_agent`(:1247) →
  `gateway/run_turn.py:2568 _run_agent` → `_run_agent_start_turn_worker`(:3059) →
  `asyncio.ensure_future(self._run_in_executor_with_context(...))`(:3121) →
  `gateway/run_turn_runner.py:1603 run_sync` → `_run_conversation_with_approval`(:1411) →
  **`agent.run_conversation(...)`(:1443)**。即 asyncio 调度 + 线程池 executor 里跑同步循环。
- **并发**：per-session `asyncio.Event` guard（`_active_sessions[session_key]`，
  base.py:3396）；忙时来事件走 `_handle_message_while_active`(:3507)，命令内联、
  文本 `merge_pending_message_event` 进 pending，turn 结束后 `_spawn_drain_task`(:4007)
  链式拉下一个（非递归）。
  - **运行中注入**：`agent/interrupt_control.py` — `interrupt()`(:93)、`steer()`(:217)、
    `redirect()`(:228)。steer = 追加到最后一条 tool result（不打断）；redirect = 只取消
    当前 model request、纠正作为 user message 追加后重试，执行工具中则降级为 steer；
    interrupt = 终止。机制是**锁 + 标志位 + 线程信号**，不是事件队列。
- **redirect 细节（追问补充）**：消费点在 `agent/turn_iteration_prep.py:316`
  `begin_iteration` 里 `agent._drain_pending_redirect()` → `_apply_active_turn_redirect`
  （`conversation_loop.py:273`）——拼 assistant 占位消息（满足 provider 的 role
  alternation，空则 `display_kind=hidden`）+ 一条 user message（transcript 存用户原话，
  发给 provider 的是带 `[Context from the interrupted assistant response]` 脚手架的
  `api_content`；raw CoT 绝不进 replayable content，否则触发 Anthropic 分类器把 session
  搞废）。生效前提 `_model_request_active.is_set()`，否则返回 False；工具执行中
  (`_executing_tools`) 降级 steer 并 `_request_yield` 请前台 terminal 交后台。
  调用方：`hermes_cli/cli_tui_mixin.py:1416`、`gateway/run_busy.py:517`、
  `acp_adapter/server.py:701`、`tui_gateway/methods_session.py:2015`。
  用户文案见 `agent/onboarding.py:36/57`。边界测试 `tests/run_agent/test_steer.py:66-99`。
- **⚠️ redirect docstring 用词不准（易误导）**：docstring 说 "partial reasoning becomes
  assistant context"，**不是 CoT**。原始思维链在流处理阶段就被 think_scrubber 剥掉，
  从没进过 `_current_streamed_assistant_text`（`stream_delivery.py:78` docstring 明写
  "Visible assistant text"；`:305` 先 `think_scrubber.feed(text)` 再累积）。
  `_apply_active_turn_redirect` 里 `_strip_think_blocks` 是第二道保险。
  `turn_api_call.py:177` 注释更直接："Never materialize incomplete signed/encrypted
  reasoning items"。保留的只是**中断前的可见回答片段**。
  重发给 LLM 的是脚手架版 `api_content`（`[Context from the interrupted assistant
  response]` + `_INTERRUPT_SCAFFOLD_MARKER` + 可见片段 + 用户纠正），
  transcript 的 `content` 仍是用户原话。空则用 `_INTERRUPTED_PLACEHOLDER =
  "[response interrupted]"``（`agent_runtime_helpers.py:2320`）。
  被取消的那次调用不计预算：`turn_iteration_prep.py:404` `api_call_count -= 1` +
  `iteration_budget.refund()`，理由是"没产出有效 assistant item"。
- **中断时是否补 assistant 消息，两条路径不同（易混）**：
  - **redirect 路径**（`turn_api_call.py:175`）：`_has_pending_redirect()` 命中就直接
    break 并置 `restart_with_redirected_messages`，**此处不 append 任何消息**；补消息
    延后到 `begin_iteration` 的 `_apply_active_turn_redirect`，且**总补一条 assistant
    placeholder**（visible 为空则 `content:""` + `display_kind:"hidden"` +
    `api_content:"[response interrupted]"`，UI 不可见），再补 user 消息。
  - **纯 interrupt 路径**（`/stop`，`turn_api_call.py:183`）：只有 `_partial`
    （strip think 后）非空才 `append_message({"role":"assistant","content":_partial})`；
    **纯 thinking 被打断 → partial 为空 → 一条都不补**，直接 `interrupted=True` 结束 turn。
  - 例外：`messages[-1]` 已是 assistant 时 redirect 不补 placeholder，把 checkpoint
    折进 user correction（`conversation_loop.py:296`）。
  - 发出去前 `substitute_api_content`（`turn_context.py:96`，在
    `chat_completion_helpers.py:1966` 调用）把 `api_content` 替换进 `content`。
  - **为什么"不补"也不会 role 断裂**：interrupt 路径 turn 直接结束、不存在重试，
    所以中断点不必补；兜底在**发请求前统一修** ——
    `repair_message_sequence`（`agent_runtime_helpers.py:556`，"pre-call belt"）4 个 pass：
    merge consecutive assistants → drop stray tool results → prune unanswered tool_calls
    → `_merge_consecutive_users`(:522，纯文本相邻 user 合并，并 `drop_stale_api_content`)。
    另：尾巴若是 tool，`close_interrupted_tool_sequence`(`message_sanitization.py:185`)
    补一条 `"Operation interrupted."`，否则不补（注释：strict providers 看到 tool→user
    会幻觉出续写）。
  - 收尾补 assistant 的条件是 `final_response and not interrupted`
    （`turn_finalizer.py:229`），所以 interrupt 时即便 final_response 有值也不补。
  即：**redirect = 立即保证（要马上重试），interrupt = 延迟兜底（turn 已结束，
  下次请求前统一修）**。

## 事件驱动 Agent Loop 设计审核（用户自述模型，我给的修正）
用户在为"生产事件驱动 Agent Loop"文章梳理模型，自述三条理解，我审核后确认+修正的结论：
- eventbus 只做有序不丢投递到 inbox，与 loop 语义解耦；handler 必须只塞 inbox 就返回，
  否则同步跑 loop 会卡死总线。eventbus 与 loop 的解耦点就是收件箱。
- 核心修正：**分类时机**。不建议"到达时分拣到 steering box / followup box"，建议延迟分类：
  消息统一进 inbox，loop 在 checkpoint 消费时才归类（step 间 drain→steering；turn 结束前
  最终 drain→降级为新 turn 输入）。用户猜"临界点 steering 自动变正常输入"结论对，
  机制是 turn 结束前的最终 drain + drain/注销同临界区 + submit 时原子查任务状态自动 spawn。
- 补漏：用户中断是第三条车道（cancel/abort 掐掉在飞请求作废当前 step），与 steering（当前
  turn 插话）、followup（排队下 turn）三车道要分开。
- 待用户回答的关键问题：UI 层要不要区分"纠正当前任务"和"排队下一件事"两种用户意图
  （决定提交时打标+边界降级 vs 全延迟分类）。
- **用户已拍板**：UI 意图只有"发消息"和"点停止"两种。结论：全延迟分类——单一 inbox
  不打标，loop 在 step-end drain 当 steering、turn 结束前最终 drain 降级为新 turn 输入；
  停止按钮是 cancel 车道（abort 在飞请求→当前 step 作废→turn 结束），走独立控制信号
  不进 inbox。

## Eventbus 谱系与 agent-loop 上行事件的优化点（讨论结论）
- 修正前提：不存在单一"真实 eventbus"设计，是谱系——进程内总线（EventEmitter/mitt，
  同步分发、无持久化、handler 抛异常消息即丢）→ 消息代理（Kafka/RabbitMQ/Redis Streams，
  持久化 log + at-least-once + 分区序 + 消费位点）→ actor mailbox（Elixir/Akka，点对点
  收件箱，常无总线）。此前"总线保证有序不丢"要自我修正：多数进程内总线不自带，靠
  同步分发保序 + 消费端队列保住，即难点始终在消费侧 inbox。Kafka 消费位点 ≈ agent
  checkpoint 的平行结构。
- agent-loop 上行事件后 eventbus 可能要做的优化：①背压（token 流高频，合并/节流/
  有界队列丢旧）；②QoS 分级双通道（命令类不可丢 vs 流式展示类可丢，避免 stop 信号
  被 token 洪峰淹没）；③并发多 task 的分区序（按 session/task 分区，别追全局序）；
  ④慢消费者隔离（每订阅者独立队列）；⑤事件信封标准化（type/session_id/seq/correlation
  id，seq 检测缺口）；⑥持久化换 replay/审计能力（事件溯源轻量版）；⑦上行必须异步
  分发防 loop 被慢 handler 拖死。
- 防过度工程提醒：单进程少任务时"每消费者一个 asyncio.Queue + 简单 emitter"就够，
  上 Kafka 级总线的条件是多进程/持久化/replay 需求。
