## agent-loop.md：message 与轨迹的关系（待用户定架构）
用户提问："默认实现里 message 是从轨迹里取的吧？压缩后是不是默认 fork 一条新轨迹？"

我的判断（已回复，等他拍板）：
- 这两个说法自洽，但共享同一个前提——**事件溯源架构**。而主流默认实现（LangGraph checkpointer、Claude Code、OpenAI Agents SDK）是**内存态 + 落盘/快照**派：热路径持有 messages 工作态，事件流只用于恢复/回放/审计，不是每轮 reduce。
- "message 从轨迹取"错在两点：①热路径不会每轮投影全量事件（靠内存态或快照）；②message 视图**不是轨迹的子集**，压缩后的 summary message 在轨迹里没有原文对应，它是 compaction 事件新生成的内容。视图是 f(events) 的结果，不是子集。
- "压缩 = fork"不成立：fork 换的是**分支/身份**（rewind、A/B 试路，原分支还在），压缩换的是**内容/视图**（原地替换，原文必须还在 events 里）。把压缩做成 fork 会丢可回溯性，正好抵消压缩的意义。
- 例外：有些实现压缩后开新 session（摘要当新会话起点，重置缓存前缀/切 provider）——那叫截断重启，不是 fork。压缩和 fork 都会破坏缓存前缀，压缩后第一轮必然 miss。
- 归因：books/python/agent-loop.md 里我写的"events 是唯一真相源，turn/step/messages 都是派生视图"是事件派立场，把用户引到了这个结论，表述含混，等他定了架构再改（热路径内存态 vs 投影，要写清 trade-off：两份状态不一致风险 vs 投影维护成本）。

## 同步架构的突出问题（用户追问，已回复）
- 先修正概念：**异步 ≠ 事件驱动**。主流 agent 框架（LangGraph、OpenAI Agents SDK）是 async + 状态机/checkpoint，不是事件驱动；把事件/中断做成一等公民的是 Pi、Claude Code 这类。async 只解决并发阻塞，不解决中断语义。
- 同步栈最致命的三条（根本无解，不只是代价高）：①不可中断——卡在 recv()，flag 没人读，停止/steering/follow-up 全无入口；②无法挂起等外部事件——HITL 审批要把线程占几十分钟，重启即丢；③用户与 agent 串行——agent 干活时用户只能干等，做不了"后台跑 + 随时插话"。
- 次要四条：并发/工具串行、状态持久化是外挂而非内建（崩了丢栈上局部状态）、错误恢复粒度粗（只能最外层 catch，无法重试第 7 步）、可测试性差（20 步要 mock 20 次 IO）。
- 分界线：任务时长长到需要**人参与**（中断、审批、插话、多 agent 协作）时，事件驱动才成为必需；短任务/批处理用同步或 async 更划算。事件驱动自身代价：状态机复杂度、调用栈断裂难调试、顺序不确定、要幂等。

## 术语约定（讨论中，待用户定）
- "同步/异步"是 **IO 模型**维度（调用是否等结果），与"控制流谁决定"正交；全 async 的循环控制流仍与同步版一致，照样不可中断。改名不能改成"异步"。
- 推荐命名：最简 loop 叫**直接式循环（direct-style loop）**，对立面是**事件驱动 / 控制反转**。备选：阻塞式循环（易被误解为"改 async 就行"）、请求-响应式 / 回合制、REPL 式。
- 用户原稿的"执行容器 + 收件箱 + 分发函数"标准名是 **Actor 模型**（mailbox + 消息处理）。按 Reactive Manifesto 分法，inbox 有确定接收者且需背压，宜称**消息驱动（message-driven）**而非事件驱动。

## "非事件驱动"那派的命名（用户真正问的）
- 他问的是：**不用事件驱动、但可以是异步的**这类架构叫什么。对立轴是"事件驱动 vs 非事件驱动"，异步不在这根轴上（异步描述等待方式，与架构形态正交）。
- 它没有响亮的专属名，因为它是默认形态——范式层 event-driven programming 的对立面就是**过程式 / 直序（procedural）**。
- 按维度可选的叫法：控制流层 **直接式（direct-style）**（PL 里 async/await 的学名即为 direct style，天然兼容异步，最贴合他的问法）；状态归属层 **调用栈驱动（call-stack-driven）**（状态在栈帧 vs 外置 mailbox）；触发方式层 **请求驱动（request-driven）**；多 agent 层 **编排（orchestration）** vs 编舞（choreography）。
- 推荐：单 loop 内部用 direct-style / 直序式；多 agent 场景用 orchestrator。

## 直序式架构搞不定的场景清单（用户要的素材，已回复）
他已列两条：及时取消、消息优先级。我补的六条：
1. **外部事件主动进来**（定时任务、webhook、文件变更、别的 agent 发消息）——直序式没有入口，只能退化成轮询。
2. **挂起等人（HITL 审批）**——要跨分钟到跨天，重启不丢；直序式只能占着线程干等，进程没了等待状态也没了。
3. **长任务跨进程存活 / rewind**——状态在栈帧上，重启即蒸发；事件驱动靠事件日志恢复、还能回退到第 N 步重来。
4. **并发子 agent 乱序回报**——谁先回来先处理，中途还能插话；直序式要自己搭并发原语。
5. **单步超时 / deadline**——粒度是步骤，到点能先存档再退；直序式只有整个 HTTP 请求的 socket timeout。
6. **重放式测试与审计**——事件流直接当测试用例和合规证据；直序式要另外插桩。
- 判别式（可作文档结论句）：**凡是需要 agent 在同一时刻容纳多个待处理意图，或者需要在两步之间停下来等外部世界，直序式就搞不定。** 直序式的心智模型是一条线，这些场景要的是"一堆待办 + 一个调度器"。

## 出站事件（agent 主动 emit，用户指出我漏了这半边）
- 我前一轮只设计了 inbound（agent 消费事件），漏了 outbound（agent 处理中主动发事件做能力扩展）。用户指出，成立。
- 出站事件分两类，**机制必须分开**：
  - **拦截类**（before_*）：即将发生，可看/可改/可否决。权限、HITL 审批、工具参数改写、上下文注入。必须同步等待、必须设超时、能短路。
  - **通知类**：已发生的事实，广播，不阻塞、不等结果、不接受否决。UI 进度、监控、轨迹、记忆提取。
- 闭环机制：订阅者可回发 inbound 事件到 agent 的 ctrl 队列——HITL 审批就是"订阅 before_tool_call → 发 interrupt"。这是"能力扩展"的真正含义：加功能不用改 loop。
- 一条流的两种用法：**agent emit 的生命周期事件就是轨迹的来源**，不另建埋点。
- 约束：拦截类订阅者应同进程（跨进程会有超时与网络失败，拦截语义难保证）；通知类可跨进程。
- 待拍板策略：拦截类订阅者失败/超时时 fail-open（放行）还是 fail-closed（拒绝）。安全场景应 fail-closed，体验场景 fail-open。
- 陷阱：别用 emit 替代直接调用（同边界原则）；事件类型要收敛并版本化，别膨胀到几百种。

## 订阅者契约（用户确认：默认行为按订阅者分别声明，不全局一刀切）
- 注册时声明：`name`（进轨迹做归因）、`event_types`、`mode`（observe | intercept）、`order`（拦截串行顺序）、`on_failure`（open | closed）、`idempotent`。
- 运行时：拦截类按 order 串行、短路、每个决定都写进轨迹；通知类并发 fire-and-forget、吞异常、best-effort 不保证送达。
- 三个易漏点：①超时用**阶段预算**而非单订阅者各算（5 个订阅者 × 50ms ≠ 50ms）；②**拦截决定必须进轨迹**（allow/deny/modify + by + reason + patch 前后值），否则事后答不出"这个工具为什么没执行"；③**回环防护**——订阅者可回发 inbound 事件，A 发 Y、B 发 X 会死循环，要 hop limit 或禁止拦截类回发触发同类拦截。
- emit 时先快照订阅者列表，避免处理途中插件热挂载导致同一次 emit 行为不一致。

## 事件总线设计（用户问"你会如何设计"）
- 先质疑要不要总线：**inbox 与总线是两件事**。判据是"发布者知不知道接收者是谁"——知道就直接塞 inbox；不知道 / 一个事件多消费者 / 接收者动态创建销毁（子 agent）才需要总线。合理形态：总线只做路由，inbox 才是 agent 的门。
- 关键决策：①拉不推（agent 主动取，一次一个事件，天然串行无锁；推会在模型调用期间造成重入）；②双队列（ctrl + 普通）而非单一优先队列（后者有乱序与饥饿，且满了控制事件也进不去）；③分区键 = session_id，同会话严格有序、跨会话并发；④总线不持久化，轨迹由 agent 自己落盘，避免两份真相；⑤事件不可变（frozen dataclass）；⑥请求-响应靠 correlation_id + one-shot future，工具调用不要绕总线；⑦边界原则——agent 内部调模型/工具直接调用，总线只在跨边界处。
- 背压：普通队列有界、满了拒绝并告知发布者（不静默丢），控制队列不设限。重试 N 次后死信。
- 过度设计红线：别上来就 Kafka（单进程 asyncio.Queue 足够，跨进程/多实例/需重放才要外部中间件）；别把内容路由塞进总线（那是 orchestrator 的决策，ESB 就是这么死的）。

## 代码自查：_interruptible 的类型标注过宽（用户问出来的）
用户问"为什么参数是 Awaitable 而不是 coro、为什么用 ensure_future 而不是 create_task"。核实结论（Python 3.13.12 实测）：
- **类型标注与执行原语必须配套**：`Awaitable` + `ensure_future` 是一对，`Coroutine` + `create_task` 是一对。混用会炸——`create_task(Future)` 直接 TypeError（实测："a coroutine was expected"）。
- `ensure_future` 是归一化入口：协程→create_task；Future/Task→**原样返回**；裸 awaitable→`_wrap_awaitable` 再包成 Task（实测三种都过）。
- **本仓库 `agent.py::_interruptible` 写宽了**：两个调用点传的都是协程（`self._llm.chat(...)` / `tool.run(args)`），没有任何调用点需要 Future/裸 awaitable。更准的写法是 `Coroutine[Any, Any, Any]` + `create_task`。属"通用性用不上"的瑕疵，未改，等用户定。
- 宽进的真实代价：`ensure_future` 收到已调度的 Task 会原样返回，于是 `task.cancel()` 取消的是调用方那个 Task——错误暴露得晚且隐蔽；`create_task` 会在边界直接报错。
- 反过来 `create_task` 有个实际优势：`name=` 参数（ensure_future 没有）。这段正好在取消任务，起名字在 `all_tasks()` 里好排查。
- 有一处**不能省**：`asyncio.wait()` 自 3.8 起弃用协程入参、3.11 起移除，实测报 "Passing coroutines is forbidden, use tasks explicitly"，所以"先包成 task"这步必须有。
- 已知边界（未修）：`asyncio.wait` 返回后若 task 恰好完成，`task.cancel()` 是空操作，但结果被丢弃（直接 raise StepInterrupted），等于白烧一次模型调用。

## 补：取消信号下沉到 IO 层（用户提醒后实施）
背景：用户质疑"为什么不是拿 turn 的 task 来 cancel"。判断结果——他前半句事实有误（LLM 调用本来就包在 `_interruptible` 里，agent.py:217），后半句方案不采纳（cancel 只能表达终止、表达不了 steering 继续；且取消点会散落到 `_emit` 拦截链里，撕在中间会造成轨迹空洞）。但他逼出的真问题成立：**cancel 只在调度层，IO 层不知道**。
改动：
- `agent.py` 新增 `CancelSignal`（asyncio.Event 包装），`LLMClient.chat` 增加 `cancel` 参数。
- `_interruptible(coro, cancel=None, grace=0.1)`：中断时**先 set 信号、给 grace 窗口让 IO 层自己停（关流收尾），超时再 `task.cancel()` 强撕**。只 cancel 不 set，被调用方来不及收尾。
- `llm.py`：`OpenAIChatLLM` **改为默认流式**——非流式下一次调用就是一个 HTTP 请求，取消只能掐连接、已生成内容全丢；流式才能在任意 chunk 停手并 `stream.close()`，服务端见断连停止生成。`_chat_stream` 按 index 拼 tool_calls 分片（id/name/arguments 都是增量，直接取首个 delta 会拿到半截 JSON），`finally: await stream.close()` 保证取消也关流。
- `ScriptedLLM` 用 `_sleep_or_cancel` 切片轮询信号（50ms 粒度），模拟真实可取消的长调用。
- 测试新增 `test_cancel_signal_reaches_the_llm`（11 个用例通过），断言 IO 层收到的是同一个信号对象。
- 纠正一处旧认知：`task.cancel()` 后 `await task` 其实会把 CancelledError 传进 httpx 栈、连接会被关掉，所以"钱照烧"说法说过头了；真正的差距在**拿不到部分结果**和**没有显式收尾通道**。

## 追问：`_interruptible` 的 cancel 参数到底买到了什么（实测结论）
用户问：cancel 传进来做什么？既然有信号为什么不直接取消？在 3.13.12 上实测四点（/tmp/probe_cancel.py）：
1. **只 `task.cancel()`，异步生成器的 `finally` 照跑，里面再 `await` 也能跑完**；连 cancel 两次都没打断收尾。→ 我 docstring 里"只 cancel 不 set，被调用方来不及收尾、连接半开"**是错的，已确认需撤回**。
2. cancel 到不了线程/子进程：`run_in_executor` 的阻塞，task `cancelled()` 为 True 但线程里的活照跑完。
3. cancel 能被吞：`except CancelledError: return x` 之后 `task.cancelled()` 是 False，cancel 白调。→ cancel 不是"保证生效"的那道。
4. 信号的真正价值是**能拿部分结果**（cancel 唯一出口是异常）+ **能到线程/子进程** + **自己挑检查点**。
当前实现的三个问题（已向用户摊开，未改）：① 两个 LLM 见信号都是 `raise CancelledError`，跟直接 cancel 等价，信号零收益；② grace 之后 `await task` 的结果被丢弃（agent.py:450-452），部分结果进不了轨迹，违反 agent-loop.md 自定的不变量；③ `tool.run(args)`（353）压根没传信号，而工具最需要它。
候选改法：A 让信号真兑现（部分结果挂 StepInterrupted 或写事件 + 信号传给 Tool.fn）／B 砍 grace 直接 cancel／C 改工厂式 `_interruptible(lambda c: ...)` 杜绝传错对象。我倾向 A+C，等用户定。

## 追问：deque + Event 而不是 asyncio.Queue（实测结论）
用户问"为什么有队列了还要信号，不能直接判断队列第一个么"。3.13.12 实测（/tmp/probe_queue.py、probe_queue2.py）：
- 单个 `asyncio.Queue`：put 后立刻 cancel getter，qsize 仍为 1，**单个队列不丢**——我原 docstring 写的"Queue.get() 被取消可能吞掉已取出的事件"这句不准确。
- 但两条 Queue 做**优先级**必须竞速两个 getter，实测 500/500 输家手里已取出的事件被静默丢弃（两个 getter 都完成时，输家那个事件既没回队列也没被用）。这才是 deque + Event 的真实理由：**Queue 只有 get() 一个出口，取出来就不能反悔；deque 把"唤醒"（Event）和"取"（同步 popleft）拆开，取之前怎么取消都不丢**。
- `wait_ctrl` 的 `while not self._ctrl` 不是多余：信号被 set 后、watcher 被调度前事件可能已被 `take_ctrl_nowait` 取走并被 `_refresh` clear 信号，少了循环 await 回来队列可能又是空的。
已把这两点写准进 `bus.py` 的 docstring（AgentInbox 类注释 + wait_ctrl），11 个用例仍通过。

## 用户质疑 Agent Loop 的 steering/followup 处理（实测核实，未改代码）
用户论点："run 从 inbox 取 event 太慢，steering 不可能注入正在跑的 turn；应该在每轮 turn 检查 steering"。逐条实测（/tmp/probe_steer2.py）后结论：
- **"不可能注入"是错的**。steering 有两条注入通路，都绕开 `inbox.get()`：① `_drain_steering()`（agent.py:229，每个 step 开头同步 `take_ctrl_nowait`）；② `_interruptible` 里的 ctrl watcher（435，LLM/工具调用期间异步打断）。实测 turn 跑到一半发 steering → 当前步被取消、文本进 history、下一步带着新指令继续，端到端注入成功。而且粒度是**每步**不是每轮，比用户要求的更细。
- **"取 event 太慢"诊断错了**。turn 期间 run 循环被 `await self._handle(event)` 挂住，压根不在 `get()` 上等；慢不慢跟 steering 无关。
- **用户说对的一半**：`_handle` 的 `USER_STEERING` 分支（206-208）只在**空闲时**触发，是条残缺路径。
- **新发现两个真 bug（实测坐实，尚未修）**：
  1. steering 打断后 `end_reason` 被 `_after_interrupt` 置为 None 且未恢复（250-251 `continue` 前没还原），若后续步因 `not response.tool_calls` 走 266 行 break，最终 `TURN_END` 的 `end_reason=None`（对照组无 steering 时是 `"stop"`）。
  2. `_handle` 的 steering 分支**不写轨迹**（对比 `_drain_steering` 411 行有 `trajectory.append`），空闲时的 steering 在轨迹里凭空消失，`replay_messages` 重建不出这条消息。实测轨迹第一条直接是 `user.input`。
- 附带：被取消的 step 只有 `model.before` 没有 `model.after`，轨迹缺少"这一步被取消"的表达。
