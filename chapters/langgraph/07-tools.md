今天主要看了一下 AI Agent Book 的 Tools 这一部分，和一部分 Agent Eval 的内容。
Tools 的这一部分我觉得讲得还是挺清楚的：

首先是从场景上对比了什么时候应该用 Tools，主要是对比 Skill。因为 Skill 其实在很多情况下也能去调用工具。具体来说：
1. 如果是一系列的操作流程，用 Skill 来封装会比较合适。
2. 对于一些相对来说复杂一些的工具使用，Skill 相当于提供了一个工具的说明文档，这种场景也比较适合用 Skill。

Tools 本身因为可以用 function call 的方式来定义工具的输入输出，如果用 Tools 来描述工具的话，相对来说可以得到更好的参数调用确定性，也更容易直接在代码层面去对模型调用工具填充的参数来做校验。

作者把工具分成了五类：

1. 查询类工具
  ◦ 常见场景：查文件、查天气、搜索、查询知识库等。
  ◦ 特点：天然具有可以并行执行的特点。
  ◦ 安全与权限：虽然不改变数据，但也需要有对应的权限管理，避免秘密或个人敏感信息暴露到模型的上下文中。
2. 执行类工具
  ◦ 常见场景：写文件、写 Todo 等会改变数据值的工具。
  ◦ 安全与权限：对工具执行的权限、本身的环境权限以及安全权限，都需要特别的防护手段。
3. Agent 间交互类工具
  ◦ 常见场景：Task 和 Sub-agent 之类的工具。
  ◦ 特点：主要用于主子 Agent 和 Task 之间的交互。
4. 用户交互类工具
  ◦ 常见场景：比如 Claude 上的 "ask_user_question" 工具，把与用户的交互定义成一个工具来直接提供交互。
  ◦ 发展趋势：目前业界可能也在研究如何通过生成式 UI（Generative UI）去和用户交互。
5. 环境/事件驱动类工具
  ◦ 特点：主要是为了让 Agent 可以更及时地感知到环境的变化，从而触发其工作。
  ◦ 常见场景：一些定时任务或轮询监控。在非用户输入的场景下，可能会把 Agent 对接到一个消息总线上，让其可以很方便地接收到外部触发来启动工作

# 如何算是一个好的工具？主要有以下几个方面：

6. 工具的描述（Description）：
这是直接用于模型推理的。要让 LLM 能够正确选择出最适合的工具，关键在于工具的描述。描述中要写清楚“什么时候该使用这个工具”，而不是在 description 里面大量堆砌工具的说明书。
7. 工具参数的定义：
参数定义要清晰，必须有明确的类型和范围。如果是在 Python 环境中，可以借助 Pydantic 来提供非常方便的定义和校验。
8. 工具的使用示例：
最好在工具说明中给出一些使用示例，特别是针对一些有特殊参数的工具。例如定义电话号码或信用卡号，它们可能有一些特定的规则。如果仅仅列出这些规则，由于不同模型的理解能力存在差异，可能会导致偏差。因此，最好在提供规则的同时，带上具体的样例说明。
